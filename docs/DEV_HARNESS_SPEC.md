**Status: revised for Dave's MVP-boundary decision and builder handoff.** Ron's 2026-10-15 scope change replaces the structure-centric framing: Phase 1 is a catalogue of engineering practices that the harness selects, installs and enforces per project. Dave has decided **Python + JS/TS**, **measured dogfood Preview before numeric caps**, and **human activation of Enforce**; new user projects default to Preview until their owner activates Enforce. ## 1. Problem, audience and completion

Coding agents need more than instructions about file length. A product change can be modular and still omit unit tests, expose an unauthorised route, ship a vulnerable dependency or apply an untested migration to production. Clayrune must let a developer select established engineering practices appropriate to their own software project, install the supporting guidance/tools, and require verifiable evidence at the right lifecycle boundary.

Every practice has two explicit halves: **guidance before work** and **a check contract**. A check may be deterministic, require an independent reviewer, or be guidance-only; the UI must distinguish them. Installing a skill never proves compliance. A clean scanner result never proves security, good test design or sound architecture. Adopt existing skills, standards and checkers before authoring project-specific glue.

The full Phase 1 programme is complete when project profiles and individual toggles select a versioned catalogue; the same effective guidance reaches Claude, Codex, Gemini and Qwen; required diff, test, CI and release evidence is collected against exact inputs; a missing/failing prerequisite holds the managed merge or deployment; and a human can grant a narrow recorded exception without weakening another gate. The six-session MVP completion contract is narrower and enumerated in section 10.1; the remainder stays in Phase 1. Clayrune is the first dogfood project. The audience includes local hobby developers and developers turning a local application into an external-facing product, MC-960's original trigger.

Sections 3-9 describe the full Phase 1 target contract. Section 10 is authoritative about delivery order and the MVP subset; requirements for later tickets must remain visibly undelivered rather than being claimed by a command-only result.

Non-goals: rewriting engineering skill packs, lint/SAST/secret rules, coverage calculators or vulnerability databases; replacing existing package managers, test runners, Git hosts, skills manager, CI or deployment systems; automatically refactoring legacy projects; universal semantic/security certification; silently provisioning staging, spending money or deploying; installing marketplace hooks/agents globally; or building the Phase 2 interactive architecture planner. The harness composes existing mechanisms; it is not a sandbox against arbitrary commands outside those mechanisms.

Product-profile activation must reconcile the actual branch/CI/release flow; it cannot label these files as already satisfying every practice. Workflow/environment changes are a later separately reviewed implementation step.

### 5.2 Test/coverage evidence contract

Every changed production path resolves to a verification group: suite argv/working directory/timeout, expected report format, source and test roots, coverage exclusions, relevant branch/line policy and required behavioral/security tests. Existing commands win. A fresh suite against the frozen candidate produces machine-readable coverage; **diff-cover** intersects executable changed lines with that report using the explicit target/base. Do not count comments/non-executable text in the denominator, silently omit untracked/new source, include coverage from another tree or accept a generated empty report as 100%.

Changed-line coverage uses a project-selected floor, not proof that uncovered logic is harmless. The previous 80% proposal remains an example for preview comparison only. Branch coverage is separately reported and enforceable only when the selected provider measures it; never convert line coverage into invented branch coverage. Test adequacy remains review. New test deletions/skips/suppression/coverage-exclusion changes require assessment and approved config activation where they weaken the bar. No automatic rebasing down of a coverage threshold and no legacy waiver for newly changed executable lines.

**Optional coverage-delta policy:** in addition to the changed-line floor, run the same approved suite/configuration/provider against `B` and `T`, recording total executable/covered lines and, where available, branch counts separately. Calculate `delta_pp = candidate_percent - base_percent` in percentage points from native report totals; require `delta_pp >= -max_drop_pp`, with tolerance chosen by the human from Preview (zero may be chosen, never assumed). Example: 72.4% to 71.9% is -0.5 percentage points; it fails a zero-drop policy even if changed-line coverage passes. The delta option never replaces changed-line coverage, so adding covered trivial files cannot excuse an uncovered changed path. Bind both results to the same tool/config/exclusion/fixture digests. Missing base reports, zero denominators, changed report scope or incompatible source mapping produce explicit N/A/Error under the activated applicability policy, never an invented zero or pass; changing coverage configuration requires human revalidation. Removing uncovered files can improve totals without improving tests, so report denominator changes for review. This option is delivered after the MVP in DH-A3; the MVP supports changed-line floors only.

V1's automatic new-route inventory is scoped to Clayrune's Flask/Python registration patterns. Other route frameworks require an explicitly reviewed manifest/test mapping or a separately validated adapter; the panel must disclose that discovery coverage. One independent reviewer can assess all applicable R practices in a single bounded review using the existing route/store. Persist a separate result and evidence reference per practice bound to `B/H/T` and the active source/config digests; do not spawn one reviewer per catalogue row or invent a new approval identity. A changed candidate invalidates those assessments while leaving the existing historical tip-review record intact.

Proof of test-first order, quality of authorization policy, useful telemetry and staging realism cannot be inferred reliably from a source diff. Keep those reviewer/runner-evidence requirements visible. The harness must report exactly what was checked, what required judgment and what is still unchecked.

## 6. Legacy debt: baseline and ratchet

Onboarding runs a read-only full scan at a frozen commit. Native-tool baselines are reused where available; the harness records normalized stable identities and approved caps without duplicating their detection logic. Structural/lint/SAST legacy allowances are distinct from vulnerability waivers and from coverage/release prerequisites. No baseline may grandfather a newly added secret, missing CI, untested migration, new authorization bypass or missing staging proof. It emits a draft ledger for actual violations, grouped by stable `(path, qualified symbol or module, rule ID)`, with measured cap/count, owner, reason, removal condition and source commit. No automatic wildcard exemption for an entire directory. Generated/vendor exclusions require explicit paths, provenance and visible policy approval; an agent cannot label handwritten code generated to escape limits.

Once activated:

1. A new symbol/file has no legacy allowance, except a verified pure relocation under rule 4. It must meet the configured limit. An object absent from the current target does not inherit a stale allowance when a later change reintroduces the same name.
2. A legacy object above the limit may remain at its accepted measurement or shrink. The allowed cap is the tighter of the active ledger cap and the current target's measured value, with the configured ordinary limit as the floor. Thus a legacy 900-line file reduced to 850 cannot return to 900 on the next change. Growth elsewhere is never offset by deleting unrelated lines.
3. New forbidden import edges or registry bodies are not grandfathered by the file's existing size allowance. Exception keys for these findings include the specific edge/body identity and exact count. An extra call inside an allowlisted function must fail, as in the provider guard.
4. Stable keys ignore line-number shifts. A deleted object retires its entry. A detected pure move carries its old cap under a recorded identity migration; it does not create a larger allowance. Ambiguous rename/split/duplicate identities require review, never automatic debt creation. New extracted files must satisfy normal limits.
5. Improvements produce a generated ledger update for review and an atomic local ratchet after successful landing. Reuse native shrink-only facilities when available; do not maintain a competing rule baseline for the same checker. The next gate also measures the current target, so an uncommitted portable-ledger update cannot reopen old headroom. Rebaselining upward requires human approval with the measured difference and reason.
6. A malformed ledger, duplicate keys, missing owners, fabricated entries or missing measurement provenance cannot activate. Stale entries must be pruned in the generated ledger; they do not exempt another symbol with the same line number. Expired temporary exceptions hold only affected candidates; unrelated existing debt is still grandfathered.

Dogfood must show that the current `agent_routes.py` can receive a within-cap bug fix while adding a new concern still needs extraction/review. The historical audit's 17,102 lines is not its current allowance. A planned extraction is its own ticket, not a prerequisite for enabling checks across the repository.

### 7.1 Snapshot and diff definition

Let `B` be the current resolved target commit, `H` the incoming tip, `M` their merge base, and `T` the proposed tree resulting from merging `H` into `B`. Freeze all full object IDs. Use `M..H` for branch attribution and changed-test signals; use `B..T` for actual integration changes. Existing-debt comparison uses `B`, not the branch's old fork point. If Git cannot resolve a base or construct a conflict-free candidate, report Conflict/Error and preserve work; do not check an older base instead.

Turn previews include staged, unstaged and untracked nonignored files in an immutable content manifest. A Git integration requires committed, clean input. A preview of dirty work never grants merge permission. Enumerate changed paths with NUL-safe Git output and preserve old/new names, deletes and file modes. No shell-interpolated filenames. Path containment, symlinks escaping the project, binary/undecodable source and resource limits yield explicit exclusions or errors according to the active policy, never a partial passing scan.

Scan whole changed files for size; imports need the approved graph/resolution inputs and affected reverse dependencies. Deleting or moving a module must still detect newly broken edges from unchanged importers. Do not merely count added diff lines. A new file must be scanned even if absent from ordinary unstaged `git diff` output. Cache by content and analyzer version, not file timestamp.

### 7.2 One standards prerequisite across landing paths

Add a leaf integration coordinator called by `agent_worktree.merge_back`, hivemind integration and the existing manual preflight tool. Reuse existing project Git wrappers, locks and worktree lifecycle. Prepare and verify `T` in a disposable integration worktree; do not merge into the user's dirty tree to discover whether it is compliant. Tests may write there, so verify the source-tree digest again after execution. Only coordinator-produced receipts count.

In Enforce mode the merge predicate is: **all applicable selected merge checks pass or have valid scoped exceptions, required practice assessments and existing review pass, required CI green, clean compatible target checkout, and unchanged inputs**. Release-stage checks that cannot exist before a build are explicitly Pending for release, not silently satisfied by the merge. Human review cannot overwrite machine results with a new `pass` string. Disabling an optional standards practice does not disable an existing project review/safety gate; profile activation must explain its review cost and prerequisite changes. Off and Preview add no standards-based merge hold and do not relax the existing merge-review gate.

Before landing, re-resolve `B`, `H`, active policy/baseline and tool versions under the existing integration serialization. Any change invalidates the receipt and recomputes the candidate. Land only the pinned commit/tree; verify the actual resulting tree equals `T`. A concurrent external Git mutation causes a hold, never approval of unexamined content. Test timestamps alone are not validity evidence.

Content-based caching is insufficient for dynamic inputs. Each applicable check declares environment and external-data dependencies plus a maximum evidence age. Dependency audits bind the resolved graph and advisory database/service observation; required CI is refreshed before landing; staging/release checks bind artifact, schema and environment. Expired or unavailable evidence becomes Stale/Error even when the source tree is unchanged. A vulnerability verdict is reproducible against its recorded database observation, not promised identical across future database updates.

Hivemind worker-to-integration merges also check standards. The existing review gate's explicit-target exemption must not become a standards exemption. The final integration-to-base move is checked again. Stale-worktree GC must preserve held/error branches and never remove them as merged. Share the same coordinator with `tools/merge-review-check.py`; do not create a competing `dev-harness-merge` engine.

Installed Git hooks remain convenience guards. Fast-forwards, `--no-verify`, cherry-picks, direct commits and other tools can bypass local hooks or Clayrune. The UI therefore says **“Enforced for Clayrune-managed integrations”**, not “all commits protected”. Expose one headless checker entry point for optional CI use; branch protection and required CI configuration remain the repository owner's separate action. A CLI report alone is not an authenticated managed-merge receipt.

### 7.3 CI and test/staging/production evidence

V1's host-status adapter targets **GitHub checks/statuses** read-only; generic CI can run the same headless checker and emit its normalized report, but a pasted report or agent-written JSON is not trusted CI provenance. Required CI identity includes repository, workflow/check and expected app/provider; configuration comes from the activated snapshot, not the candidate removing its own failing workflow. Missing jobs, workflow skips, timeout, rate limit, permission failure and stale commits hold the selected gate. Record check/run URLs, commit IDs and conclusions; use existing vault-by-name credentials, never tokens in argv or reports. No workflow dispatch, remote push or credential creation is implied by a read-only check.

For branch-tip CI, a pass on `H` covers `H` only. The combined candidate `T` still needs its local configured checks, or host merge-queue CI on a merge-group commit whose tree matches `T`. A moved target invalidates candidate evidence. The [GitHub merge queue documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) describes `merge_group` workflows; the harness must discover the repository's actual setup rather than assume them. A GitHub-less project with CI required remains Unconfigured until the user connects a supported adapter or changes its selected policy; local tests are not substituted for remote CI.

An environment receipt identifies the approved non-production runner/environment, fixture/database schema fingerprint, command/tool/config digests, source/artifact digest, time and result. Avoid recording secret values, raw customer data or full sensitive connection strings. Environments use separate non-production secret references; neither renaming a production URL nor claiming `staging=true` provides evidence. Before coding, the test-environment receipt proves setup/fixture health, not future code correctness. After build, staging and migration receipts bind the exact artifact and schema to be released. A migration rehearsal must actually execute against a disposable, representative non-production database and exercise recovery/compatibility; dry SQL output alone is insufficient.

Accept remote evidence only after the read-only host adapter verifies its producer run/job, approved workflow/config identity and associated source/artifact IDs against the active policy; bind downloaded report hashes to that run. Local environment evidence comes from the coordinator's registered job/runner. Agent-posted receipt JSON, pasted logs, unverified uploaded artifacts and a filename containing “staging” cannot establish provenance. Configuring a new trusted producer is a human policy activation, not a capability a builder grants itself.

The harness integrates its **pre-production check** into the user's existing approved CI/deploy pipeline; it does not create a new deployment orchestrator. The production job must depend on that gate and retain existing environment protections/human approval. If that dependency cannot be verified or installed under the user's authorization, the panel says **Deployment enforcement unavailable**, and an external-facing profile cannot claim the no-direct-to-production practice is enforced. Local managed merge checks, prompt rules and a CI YAML file alone do not establish a production boundary. Direct external deploys or users removing their own branch/environment protection remain outside Clayrune's control; no claim of universal blocking.

Where a project registers a deployment target, migration/staging requirements remain applicable even if its starting profile was Local hobby; switching profile is not a route around an already active production gate. New staging resources, paid runners, production mutations and outward-facing configuration changes follow the existing human authorization rules. Missing production evidence cannot be repaired by borrowing a different artifact/environment's result.

### 7.4 What staging means for a local-first project

Staging is a **separate non-production execution target**, not necessarily a hosted service. A local CLI/library can use a disposable worktree plus isolated interpreter/package environment and synthetic files; a desktop/local server can use a separate data/config root, test port and disposable database, then install/start the built package there. Never start another instance against the user's live data or the Clayrune hosting port. A container is optional, not an assumed isolation guarantee. The approved recipe identifies paths, ports, schema/fixtures, external-service stubs or sandbox accounts, expected health/test results and cleanup ownership. A local environment can satisfy P03 and, when it exercises the actual candidate artifact/config class, the applicable P04/P22 release rehearsal.

For local-only software, “production” means the user's live install/data, or the artifact distributed to other users. Rehearse migration on a synthetic or explicitly authorised sanitised copy before touching that live store. Do not create a second environment merely to rename the same resources: if isolation cannot be established, report Unconfigured and hold the selected prerequisite. A non-deployed library may mark hosted-deployment evidence N/A with a reviewed applicability reason; its test/package-install checks still run. Once a remote target exists, local smoke alone cannot attest to remote IAM, network, managed-database or capacity behavior; require corresponding non-production evidence for those risks.

The runner can enforce setup/test order inside managed jobs; the integration coordinator can hold a managed merge; a registered protected pipeline can hold its production job. It cannot intercept every shell command, stop an owner manually copying a file, or prove that an arbitrary user-supplied environment label is isolated. Show the exact boundary and missing prerequisite. No test environment, staging resource, production mutation or server restart is created by this spec. MVP runs approved local environment smoke commands as checks; dispatch-time gating and authenticated artifact-bound deployment receipts arrive in DH-A6/A7.

## 8. Findings, repair and human exceptions

### 8.1 Results and receipts

The evaluator returns structured `pass`, `fail`, `error`, `pending`, `review_required`, `unsupported` or `off` status, plus per-practice and per-rule outcomes. Disabled, N/A, guidance-only, reviewer-required and deterministic pass must remain separately visible. The CLI maps a completed pass to 0, blocking findings/review-required to 1, and inability to evaluate to 2. Pending is a job state, not exit 0. Unsupported selected blocking checks prevent a complete pass.

Proposed new HTTP contracts, not endpoints available today: `GET .../dev-harness/catalogue` lists descriptors/profiles and per-entry provenance/coverage; `POST .../dev-harness/install-plan` resolves a draft without installing; `POST .../dev-harness/install` executes a human-approved pinned plan through existing skills/jobs/toolchain owners; `GET /api/project/<pid>/dev-harness` returns effective mode/revision, editable draft and language coverage; `POST .../dev-harness/preview` starts a read-only evaluation and returns 202 with run/job IDs; `GET .../dev-harness/runs/<run_id>` returns its status/evidence; `POST .../dev-harness/activate` accepts an expected active revision, validated draft and measured baseline digests plus existing human proof; `POST .../dev-harness/exceptions` creates the exact finding exception; `DELETE .../dev-harness/exceptions/<id>` withdraws an unused exception through the same human gate. Exceptions are post-MVP (DH-A9), not stub endpoints returning success. Draft editing stays in the shared panel until activation; saving a repository draft cannot activate it. Revision conflicts return 409 without partial writes; refused human actions return 403; invalid policy returns 400. Runs use the existing managed-job implementation and notifications, not another queue. The existing review route carries the structured selected-practice assessments described in section 5, checked against the current coordinator candidate; this richer assessment arrives in DH-A5 while MVP preserves the existing independent verdict.

Each receipt includes project/run IDs, practice ID/source/rule/tool/config versions and machine/reviewer/guidance coverage; stage; `B`, `H`, `M`, `T` or preview manifest; policy/baseline/checker digests; executed verifier argv IDs, durations and exit codes; findings; required-review references; exception IDs; and creation time. A finding includes rule ID, path, qualified symbol/edge, display line range, observed value, cap/baseline delta, severity and one concrete repair. Example: “`size.function`: `src/importer.py:load_batch`, 104 lines; allowed 80; extract decoding from persistence.” Reports must escape paths/messages, limit resource use and redact secret values from output.

Persist local receipts through existing atomic storage and activity logs. Crashes or unreadable records cannot become passes. Jobs survive a chat ending through Clayrune's existing job/completion mechanism. UI events are project/run scoped so a late response cannot paint another project's badge green.

### 8.2 Repair and escalation

A failed check preserves the branch/artifact and displays the report on its existing agent/session surface and the project standards panel. Return the report and check command through existing follow-up/job delivery, retaining persona and worktree identity. No unsolicited duplicate repair session. An already authorized builder can fix and rerun; a finished builder requires its lead to dispatch a fresh bounded repair task using the existing dispatch path.

No automatic retries beyond the owning task's existing authorization. Two unchanged failed attempts are summarized for the lead; a new exception is not inferred. Agent/lead choices may resolve implementation questions, but cannot approve policy weakening or human exceptions. Unattended logging uses `docs/_journal/<item-id>-<slug>.md`, never backlog-note spam. Existing notification/decision channels handle the human interrupt.

### 8.3 Narrow human override

The user can choose **Fix**, **Request repair**, or **Allow this finding once**. The last action requires the existing human-only caller check and per-call passcode proof; a body field, Origin claim or agent-written file is insufficient. New routes must reuse the current helper and preserve its host/passcode bootstrap behavior. No agent path creates, extends or approves an exception.

A one-time exception binds exact project, practice and rule/finding keys, scope (`setup`, `merge` or `release`), `B/H/T` where applicable, artifact/schema/environment identity for release, policy digest, human reason, owner, expiry and approver evidence. Proposed default lifetime: 24 hours, consumed by one successful gated action. It cannot authorize a different tip, target, artifact, environment or policy, and it never deletes the underlying finding. Unrelated blocking rules and the existing review gate still apply. Error states with no complete scan cannot be waved through using a finding exception; repair the tooling or deliberately change the project's active mode through the human safety surface. A human can withdraw an unused exception; after landing, reversal is a normal reviewed revert, not automatic history rewriting.

Permanent threshold/exclusion/baseline changes are policy activations with visible diffs, not “Allow once”. Off/Preview/Enforce transitions are human-only, audited and invalidate outstanding receipts. This gate grants no deployment, credential or publishing authority. A finding exception cannot replace required external environment approval, authorise an untested production mutation or waive unknown/incomplete evaluation. Any policy transition that would remove production controls must name those lost protections in the human confirmation; it never changes the actual CI host's protections by itself.
