# Usage Breakdown Dashboard

**Status:** Proposed specification, MC-998, 2026-09-28. No implementation is implied by this document.

## Problem and user

The existing Usage surface shows provider allowance percentages and Clayrune token totals, but cannot answer which projects, characters, triggers, and models produced the recorded work. Ron and other Clayrune operators need a breakdown they can inspect on desktop or phone without mistaking an account-wide vendor percentage for usage caused by Clayrune alone.

**Outcome:** For a selected provider, allowance window, and time range, the user can see observed input, cache, and output tokens; source-code lines added and deleted; rankings by project, character, trigger, and model; the observed change in the vendor bar; and an explicitly unattributed portion. Every number carries its source and coverage state.

## Existing contracts and measured baseline

- `system_routes.system_usage_get` supplies Claude's `usage_limits` (5-hour, 7-day, and scoped windows) from `_fetch_oauth_usage_limits`; Codex weekly and 5-hour figures come from the most recent rollout record through `_fetch_codex_weekly_usage` and `_fetch_codex_usage_detail`. These reads are cached for 60 seconds and are **not persisted as a time series**. Codex `sampled_at` currently uses the rollout file mtime. `provider_weekly_usage` contains only providers with a real weekly percentage; Gemini has no such source.
- `agent_routes.api_usage` reads all `*_agent_log.json`, prefers nonzero transcript-derived `input_tokens`/`output_tokens`, and falls back to nested `usage`. Its flat total omits cache categories and cannot group by project, character, trigger, or model. `_mc_usage_from_agent_logs` requires nonempty `model_tokens` and therefore skips Codex rows whose nested usage is populated but transcript telemetry is empty.
- `_log_agent_completion_body` writes project-local rows with `ts`, `started_at`, `provider`, `character`, `trigger_type`, `model`, `observed_model`, `usage`, `cost_usd`, `num_turns`, flattened token fields, and `model_tokens`. Older or interrupted rows may lack many of these. `agent_log_max_entries` defaults to 500 **per project**, so logs alone cannot support reliable long-range history. The transcript extractor in `mc/memory.py` supplies Claude model totals as input plus output and separate cache reads; it does not supply per-model cache or output breakdown.
- The current desktop bottom strip opens the Usage tab in the system-status popover; mobile reaches the same renderer through `openSystemUsage()` because the strip is hidden at widths at or below 960px. The frontend polls `/api/system/usage` every 60 seconds while open.

Codex's nested usage contains `input_tokens`, `output_tokens`, and `cached_input_tokens`; its flat telemetry fields are zero in all 119 retained rows. Gemini's adapter stores a `result.usage` or `result.stats` object when a turn ends, but this checkout has no Gemini log row with which to verify the persisted shape. A Gemini percentage and a Gemini historical total must therefore remain unavailable until real samples exist. A zero in a legacy row or an in-progress Codex row does not prove zero consumption.

## Scope and source rules

1. The dashboard must separate **observed Clayrune activity** from the **vendor account allowance**. Rankings use observed session facts. A vendor percentage may be attributed only as a labelled estimate over measured intervals; the UI must never imply that its sum of project rows equals the whole bar.
2. The user must select one provider and one window: Claude 5-hour, Claude weekly all-model, Codex 5-hour, or Codex weekly when that window has a real source. Scoped Claude weekly windows may be shown with their own samples; they must not be combined with all-model windows or attributed to mixed-model sessions without per-model usage. Providers without a bar still get observed-token rankings if their telemetry exists, with percentage metrics marked unavailable.
3. The default view is the current weekly window for the provider whose strip bar was opened. The range can be the current window or any completed window retained in the last 90 days. The 5-hour and weekly percentages, reset times, and provider account are independent series. No cross-provider token or percentage sum is presented as a plan total.
4. Incognito sessions remain excluded because they have no durable agent log. Housekeeping and internal child sessions must have an explicit inclusion flag in the fact record so the user can tell whether their work is included. The default includes every persisted run, including dispatch children, exactly once; a parent is not charged its child's tokens again.

## Metrics and computation

| Metric | Computation and display contract |
| --- | --- |
| Input tokens | Claude: fresh `input_tokens` plus `cache_creation_input_tokens` plus `cache_read_input_tokens`, displayed as **fresh / cache write / cache read**, with a separate processed-input total. Codex: `usage.input_tokens` is the input total; `cached_input_tokens` is a subset and must **not** be added again. Other providers: use documented adapter fields only; retain raw category names when semantics are unverified. |
| Output tokens | Sum the provider's captured session output tokens. Show reasoning output as a subset when supplied, never add it twice. A missing `usage` or failed parse is `Unavailable`, not zero. |
| Tokens per 1 percentage point | For each eligible same-provider, same-window sample pair, divide Clayrune's observed processed input (and separately output) during the interval by the vendor's positive utilization delta in **percentage points**. Also retain `workload = processed input + output` divided by that delta for estimated shares; this is a proxy, not the vendor's weighting formula. Display median and 10th–90th percentile of interval ratios, sample count, date range, and `Indicative: account-wide bar`. Do not calculate with a zero or negative delta. Do not present this as a vendor exchange rate or conversion rule. |
| Bar change | `later.raw_utilization - earlier.raw_utilization` within one uninterrupted vendor window, in percentage points. Preserve vendor precision; never use the rounded strip label, an `exhausted` UI overlay, or a stale cached read as a sample. |
| Lines of code | Git `--numstat` additions and deletions in source files attributable to the session's isolated branch/worktree commits or isolated end-of-session diff. Show **added** and **deleted** separately; added is the requested “lines written.” Count `.py`, `.js`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.jsx`, `.html`, `.css`, `.scss`, `.swift`, `.kt`, `.java`, `.rs`, `.go`, `.sh`, and `.ps1`, including tests. Binary files, generated/lock files, vendored directories, docs, and other extensions are excluded. No git evidence means `Unavailable`, not zero. |
| Rankings | Group deduplicated session facts by project ID, character identity, trigger class, observed model, and provider. Sort by processed input by default; allow output or added lines. Show `Unknown` group and missing-data row counts for each dimension. A multi-model session contributes to a model only where per-model numbers exist; otherwise group as `Mixed/unknown`, never assign all usage to a requested model. |

The ingest must keep both raw values and normalized values with a `source`, `captured_at`, and `coverage` flag. The project ID comes from the owning agent-log filename or the live session, never from the task text. Prefer complete transcript totals for Claude only where extraction and message-ID deduplication are verified; use nested `usage` for Codex and Gemini. Do not sum transcript and nested totals. A reported numeric zero is valid only when a completed usage event confirms it; an empty dict or defaulted flat zero is missing data. Check the provider's cumulative-versus-per-turn semantics before folding updates: Claude Mode B accumulates per-turn results, while Codex's turn-completed usage is a thread running total with an existing carry on rollover. Deduplicate by MC `session_id` and update a single fact at each completion/checkpoint; a different provider thread or Scribe checkpoint must not create another charged session. Legacy rows without a stable MC session ID may be imported only with an explicit low-confidence synthetic key and a duplicate check against native session IDs.

### Percentage attribution and uncertainty

The vendor does not publish a stable mapping from token categories to allowance percentage. Cache weighting, model choice, tool calls, vendor-side accounting, allowance adjustments, and usage outside Clayrune make a percentage split causal inference, not a fact.

- An interval is eligible for the tokens-per-point distribution only when both endpoints are fresh original vendor readings, have the same provider/window/reset identity, are at most 10 minutes apart, show a positive delta of at least 1 percentage point, and have complete Clayrune session-token coverage. Windows that reset, percentages that fall, gaps, stale Codex rollout observations, and intervals crossing an allowance adjustment are excluded with a reason count. An interval with no Clayrune activity contributes its positive change to `Unattributed activity`; it contributes nothing to calibration.
- A calibration value requires at least five eligible intervals from at least three distinct sessions in the same provider/window class. Those intervals must have only one Clayrune session active. External use cannot be proven absent, so even these ratios are **apparent rates**. The 10th–90th percentile is an observed spread, not a statistical confidence interval or a bound on outside use. With less evidence, display `Insufficient samples`.
- For a displayed window, estimate each session's bar contribution as its observed workload divided by the median calibrated workload-per-point for that provider/window class. Compute an indicative range by dividing the lower proxy (`fresh input + output`) by the calibration's 90th-percentile workload-per-point, and the upper proxy (`all processed input + output`) by its 10th percentile. This range reflects observed rate variation and cache treatment; it does not bound outside use. Intervals with overlapping Clayrune sessions may be split only in proportion to these estimated workloads and must be marked `Overlapping sessions`; all affected project shares remain approximate.
- `Unattributed / uncertain` is always a visible bucket for the difference between observed vendor bar movement and estimated Clayrune movement. It includes plain CLI, vendor web/app use, missing logs, and model/accounting error; the system cannot tell those causes apart. Never spread this remainder across projects. If estimated Clayrune movement exceeds the observed delta, show `Estimate exceeds observed bar change` and the excess as an error indicator rather than clamping it away or inventing a negative external bucket. If no valid calibration exists, put the entire bar change in `Unattributed / uncertain` while still showing direct token rankings.
- Show raw percentage precision and an endpoint-rounding band of plus/minus half the smallest reported unit at each endpoint. The resulting delta band is additive. This band covers display quantization only; outside activity and unknown vendor weights are separate, unbounded sources of uncertainty. Use the observed 10th–90th rate spread for the displayed estimated-share range, with this caveat visible next to it.

## Sampling and durable facts

Use a local `data/usage_breakdown.sqlite` file, outside `DATA_DIR` (`data/projects/`), with schema-versioned tables for `allowance_sample`, `session_fact`, and `code_delta`. Add this path and SQLite WAL sidecars to `.gitignore` when implemented. It must contain no OAuth token, credential, prompt, transcript, source text, or task summary. The server writes transactions atomically; the dashboard reads snapshots. This store is a 90-day measured record, not a replacement for the existing agent log or the proposed general `data/mc.db` migration.

- Sample at server startup, every 60 seconds while any provider session runs, every five minutes while idle, and immediately after a completed turn or session. Sampling runs server-side even with no dashboard open. Share the existing 60-second vendor fetch caches; a cache hit is not a new sample. Claude samples use the actual successful OAuth response time. Codex samples use the event timestamp from the latest `token_count` record, not a repeatedly polled rollout-file mtime; identical event identity/timestamp/values are stored once. A manual refresh may request a fetch but must not turn an unchanged source into another observation.
- Store provider, account-safe local identifier if available, window kind/scope, raw utilization, `resets_at`, actual source observation time, server receipt time, source version, and quality/error state. Validate finite 0–100 values. Do not interpolate across missing samples or vendor reset changes. If a provider exposes no percentage, record availability metadata without synthesizing a bar.
- Capture normalized session facts on start/checkpoint/completion, including provider, project, character, trigger, requested and observed model, start/end times, status, each available token category, and field-level provenance. Continue updating the same fact while a session is live. Preserve facts for 90 days after completion even when the project's 500-row log cap prunes the original; historical backfill from retained logs must be marked partial and must not invent earlier allowance samples.
- Prune raw samples and session/code facts older than 90 days in bounded batches. Keep no 90-day aggregate that implies coverage before first sample. The UI shows `Coverage begins <date>` and gaps. A reset inside the retention span starts a new window; the dashboard never differences samples across that boundary. Persistence errors must be logged, and the UI must mark the affected interval incomplete rather than silently reporting zero.

## Trigger and code attribution

Map actual `trigger_type` values to UI labels: `manual`, `schedule`, `workflow`, `dispatch`, and `hivemind_orchestrator`/`hivemind_worker`. `Steward` is a subtype of a scheduled run: classify only when the first task has the canonical `[Steward cycle]` marker or a future explicit steward flag. Keep `Scheduled (other)` separate. Legacy missing triggers remain `Unknown`; do not default them to manual. A dispatch child's work belongs to its own character/project/trigger row, with an optional link to its parent.

For code lines, capture the session's worktree and baseline commit/dirty state at dispatch. At completion, collect the session's own commit SHA set and a final isolated diff **before** any automatic merge-back. Use git numstat on those changes once per session; exclude pre-existing dirty changes. If the session shares a checkout with concurrent writers, cannot resolve its own commits, or has an ambiguous dirty diff, mark lines unavailable and explain why. Count renames by the resulting numstat additions/deletions, not as a whole new file. A later merge, cherry-pick, or commit replay must not count the same session's lines twice. Do not infer LOC from token output or text length.

## Dashboard layout and states

**Entry point changed by Ron 2026-09-28.** The desktop bottom bar no longer navigates anywhere on click — Ron called that overkill for a glance. Hovering (or focusing via keyboard, or a click/tap toggle) a provider's bar shows a small ~280px summary popup anchored to that bar: its current window + % used + reset time, top 3 consumers by character with share of measured tokens, top 2 models, `Other` and `Unattributed` lines (always shown), session count and average tokens per session. Once the calibration gate has passed each consumer line shows its estimated % of allowance; before that, token shares only plus one muted line noting how many more clean samples are needed. Incomplete coverage and no-data-yet states get one honest line each, never a silent gap. Esc or an outside click closes it; the popup ends with a `Full report ->` link. The full `Breakdown` section below is the secondary, detailed surface — it moved OUT of the Usage modal entirely into its own Advanced-sidebar entry ("Usage report", `sidebarNav('usage-report')` / `openUsageReport()`), reachable the same way on mobile via the drawer. The Usage modal itself keeps only the bars and windows.

The full report shows compact observed input/output/LOC totals and coverage; `Tokens per 1%` with spread and sample count; a segmented bar of estimated Clayrune work and `Unattributed / uncertain`; then one ranking table with a dimension selector (Project, Character, Trigger, Model, Provider) and metric sort. Rows open the contributing sessions and show unknown counts. The provider view never places Claude and Codex percentages on one shared scale.

On desktop the ranking fits its own modal with a scrollable table. On phone it uses the same data and renderer as stacked rows with the selector and metric control pinned above the list; no horizontal table scroll is required. Empty states distinguish `No runs`, `Telemetry unavailable`, `No vendor percentage`, `Sampling has not begun`, and `Insufficient calibration`; all show observed data where present. Freshness and gaps appear beside the affected metric, including Codex's last real source observation time. Refresh changes no historical reading.

## Privacy and non-goals

All facts, samples, and calculations stay on the host and are served only through Clayrune's existing authenticated local/remote session. Nothing is sent to an analytics service. The existing vendor usage fetch remains the only vendor-facing request; this feature must not transmit project identity, task text, repository paths, or source diffs to a vendor. The local store must not enter Git, installer bundles, or exported diagnostics by default. UI project/character names follow existing access controls.

Out of scope: calculating a vendor's private billing formula; proving which external app consumed a percentage point; reconstructing percentage history before sampling begins; treating lines added as accepted or useful code; inventing Gemini/Qwen allowance bars; equating costs across subscription and API-key accounts; or changing allowance enforcement and reset controls.

## Acceptance checks

1. A Codex row with nested positive usage and zero flat telemetry contributes once to observed tokens; a Claude checkpoint and its completion contribute once; absent Gemini data displays unavailable, not `0`.
2. Two percentage samples separated by a reset, stale Codex observation, or missing interval produce no tokens-per-point ratio. A positive vendor delta with no Clayrune run appears in `Unattributed / uncertain`.
3. Simultaneous sessions never yield exact project percentages. A shared dirty worktree yields `LOC unavailable`, while an isolated branch with one source-code insertion and one deletion reports added 1, deleted 1.
4. Desktop strip and mobile Usage entry reach the same breakdown and show the same provider/window, freshness, unknown groups, and coverage date. No new local state is written under `data/projects/`.
