#### 1a. `mc/secrets_store.py` (read fully, 2874 lines)

**P1 — `mc/secrets_store.py:2567-2569`, `:2009-2015`, `mc/core.py:132` — E — medium.
Every secret read rewrites the whole store and spawns two `icacls` processes, under the vault lock.**
`get_secret_value` bumps `last_used_at`/`use_count` and calls `_save_store`
on every dispense. `_save_store` → `_write_private_bytes` hardens the temp
file and the final file, and on Windows each `_harden_secret_perms` is one
`icacls` subprocess. All of it runs inside `with _lock:`, so every other
vault read and the audit append wait behind it. **Measured** (scratch
`CLAYRUNE_HOME`, file backend, 30 entries, Windows): 35 ms per read, 2
`subprocess.run` per read, 2 store loads per read. A command with five
placeholders is five full store rewrites and ten `icacls` spawns
(`resolve_placeholders`, `:2693-2700`). A store that cannot be written (disk
full, ACL damage) also fails the read, although the decrypt already succeeded.
Smallest fix: harden only when the file is created (the ACL survives
`os.replace` of a file that was hardened as a temp only if the temp is
hardened, so harden the temp once and drop the second call), and move the
usage counters to a sidecar or batch them so a read is not a store rewrite.
Tests: none measure it; `tests/test_secrets_store.py` asserts the counter
value only.

**P2 — `mc/secrets_store.py:2203`, `:2217-2218`, `:1982`, `:785` — E — low.
`list_secrets(check_readable=True)` re-reads and re-parses the store 2N+1 times.**

`load_master_key` (a second `_load_store` in non-passphrase mode, plus one OS

read, not measured). Smallest fix: load the store and the key once in
`list_secrets` and trial-decrypt each record against them. No test counts
loads.

### 2. Local passcode gate: `mc/blueprints/local_auth.py` (read fully, 485 lines)

The passcode is two things at once: the LAN login, and the "a human is
asking" proof for every vault write, the vault lock routes and the
attend-once grant (`secrets_routes._require_human_passcode`). The findings
below matter because of the second role.

**P19 — `mc/blueprints/local_auth.py:324-327`, `:346` — L — high.
Until a passcode exists, any loopback caller can set it, and it then holds the human proof.**
First-time `POST /api/local-auth/set` requires only an exempt origin, and
every process on the host is exempt (`:154-156`). On an install where the
owner has not set a dashboard passcode, an agent's `curl` sets one of its
choosing; with that passcode and an `Origin` header (which
`mc/unattended.py:is_unattended_caller` accepts as proof of a browser) it
passes every gate in `secrets_routes.py`: create a secret, flip
`allow_unattended`, set the vault passphrase and receive the recovery key.
That is a path around vault rule 3. `docs/SECRETS.md` records the same
window for `vault-lock/set` and answers it with a push
(`_notify_vault_tamper`); this route writes one log line (`:347`) and
nothing else, and a secret created afterwards notifies nobody. The steward
fence refuses the route by name (`steward/fence.py:3930`,
`_HUMAN_GATE_ROUTE_RE`), so a fenced cycle is stopped; an unfenced session
is not (which sessions are fenced: section 5). The owner learns of it only
when Settings asks for a "current passcode" they never set. Smallest fix:
make the first set a human-presence step as well: accept it only with a
one-time code the server prints to its own console/log at boot or shows in
the desktop window, or only from the passkey-verified path; and push on
every passcode set, as the vault does. No test covers "agent bootstraps the
passcode"; `tests/test_local_auth*.py` assert that a LAN device cannot.

**P20 — `mc/blueprints/local_auth.py:74-80` — M — medium.
A passcode file that fails to read or parse is treated as "no passcode set", silently.**
`_load_local_auth` swallows every exception and returns `{}`. Consequences
of one unreadable or damaged `data/local_auth.json` (a crash-truncated
file, a sharing violation during another writer's replace): the gate tells
LAN devices the dashboard was never set up; `local_auth_set` takes the
first-time branch, so the next loopback caller sets a new passcode with no
proof of the old one (P19 without the precondition); and
`_local_auth_set_passcode` (`:105`) starts from `{}` and overwrites the
file. Project policy requires a log line on a state-file load failure;
there is none. Smallest fix: distinguish "file absent" from "file present
but unreadable"; on the latter log and fail closed (configured = true,
verify = false), never fall into bootstrap.

**P21 — `mc/blueprints/local_auth.py:51`, `:56-57`, `:208-230` — L — medium.
The human-proof passcode may be four characters, allows 2,880 guesses a day from the host, and a wrong guess leaves no trace.**
The budget is 10 failures per 300 s per source IP. Every local process and
every tunnelled request shares the one address 127.0.0.1, so (a) a
co-resident process gets 10 guesses every five minutes, which exhausts a
4-digit passcode in under 3.5 days (10,000 / 2,880); (b) those same wrong
guesses lock the owner out of every passcode-gated action for the window;
(c) neither a failed attempt nor a lockout is logged or pushed
(`_local_auth_release` records a counter only), so (a) is invisible. The
PBKDF2 hash sits in `data/local_auth.json`, readable by the same user, so
an offline search is faster still; `docs/SECRETS.md` lists that residual.
Smallest fix: log every failure and push on lockout; raise the minimum for
installs that have a vault passphrase; make the lockout window grow on
repeat.

**P22 — `mc/blueprints/local_auth.py:159-165`, `:288` — E — low.
A LAN request reads and parses the passcode file two or three times.**
`_local_auth_is_configured` and `_local_auth_verify_cookie` each call
`_load_local_auth`; a refused request calls it a third time. Loopback and
tunnel requests return before any read. Read, not measured (file is under
1 KB). Smallest fix: load once per request, or cache on mtime.

Sound in this file: changing an existing passcode needs the current one
from every caller, exempt or not (`:328-345`); the admit/release pair
bounds concurrent guesses and cannot leak a slot (`:168-248`); the cookie
secret rotates on every passcode change (`:108-110`); the peer address is
the TCP peer, not a forwarded header.

429 the owner's own add / revoke / enroll". It still can, with fewer calls:
**measured**, six `assertion` ceremonies from `127.0.0.1` and the seventh,
the owner's, is refused `too many ceremonies pending for this client`. Six
forged-header POSTs to `/api/passkeys/assert/options` every 120 s keep the
owner out of add and revoke for as long as the caller likes; no proof is
needed to issue one (`passkey_routes.py:322-366`). Needs one enrolled
passkey and a same-box process, which can do worse elsewhere, hence low.
Smallest fix: key the cap on the browser-session nonce cookie (a caller with
no prior cookie gets its own small bucket) and evict the oldest pending
ceremony for a client instead of refusing the new one.
`tests/test_passkeys_prerequisites.py` exercises the cap with distinct
client strings, which the routes never produce.

**P24 — `app.py:492`, `:588` vs `mc/passkeys/host_check.py:67`, `:70` — F — low.
The desktop entry point opens the dashboard at `127.0.0.1`, where passkey enrollment is always refused.**
`app.py` loads `http://127.0.0.1:<port>` in both the webview and the
fallback browser; the host check accepts only Host `localhost:<port>` and
Origin `http://localhost:<port>` (correctly: the RP ID is `localhost`, and
an IP is a different site to WebAuthn). A user of the packaged app therefore
always gets `bad_host` and the "open http://localhost:<port>" message; the
feature works only from a browser tab they open by hand. Read, not measured.
Smallest fix: open `http://localhost:<port>` in `app.py` (the server binds
loopback either way), or have the panel offer the link. Not covered by a
test.

**P25 — `mc/passkeys/__init__.py:1-19`, `mc/passkeys/ceremony.py:13`, `mc/blueprints/passkey_routes.py:114-115` — M — low.
Stale package description, and a read that writes.**
The package docstring says there is no assertion verifier and lists five of
the eight modules; `assertion.py`, `integrity.py` and `recovery.py` exist
and are wired. `_store_failure` writes a log line and an audit line for a
refused registry, and `GET /api/passkeys` calls it, so every Settings open
(and any unauthenticated loopback GET) appends to `audit.jsonl` while the
registry is refused; the file has no cap. Smallest fix: correct the
docstrings; audit the refusal on write routes only.

Limits that are stated in the code and that I confirmed rather than found:
attestation is `none` and every header in the host check is forgeable by a
same-box process, so the first enrollment is exactly as strong as the
passcode (see P19: a process that sets the passcode can also enroll a
software credential, and after that add/revoke need *its* assertion, with
`recover` the owner's only way back); deleting both registry files reads as
a fresh install (`integrity.py:18-21`).

Sound here: the ceremony is consumed before any check, so every failure
spends it (`challenges.py:116-128`); the proof is bound to one purpose and
one target and never downgrades to the passcode
(`assertion.py:126-127`, `passkey_routes.py:137-155`); the counter is
re-checked under the write lock (`store.py:549`); a registry that is
missing, unsigned, rolled back or half-written is refused, not read as
empty (`store.py:222-259`); `reset` re-checks "already refused" under the
lock and moves, never deletes (`recovery.py:39-58`); the lock-file break
compares identity under a breaker (`store.py:271-312`); request shape is
checked before the passcode so a malformed call costs no guess.

### 4. Backup, export, import, restore points: `mc/backup.py` (2165) and `mc/blueprints/backup_routes.py` (712), both read fully

Reproductions ran against a temporary home and data root, through the module
and, for the routes, a Flask test client holding only this blueprint (no

**P26 — `mc/blueprints/backup_routes.py:577-588`, `mc/backup.py:1346-1365`, `:1460-1463`, `mc/secrets_store.py:2730-2777`, `mc/unattended.py:76-85` — L — blocker.
`export-project` with `vault: true` hands a project's secrets to any caller, sealed under a passphrase the caller picks, with no human proof.**
Restore, import and rollback were given the retyped passcode (MC-995,
`:546-550`, `:616-618`, `:692-698`); the one route that *reads the vault out*
was not. Its only gate is `is_unattended_caller(project_id)`, which is false
for any request with an `Origin` header, for a manual-chat agent, and for an
unattended agent whose session is on a different project. The export then
opens every entry scoped to that project with `_open` directly, so
`allow_unattended=false`, the per-read audit line and the `oauth.*` deny in
`get_secret_value` are all skipped; one `export` audit line is written.
**Measured**: `POST /api/backup/export-project/<id>` with `{"vault": true,
"vault_passphrase": <caller's>}` and no passcode → 200; the archive's
`secrets/vault.enc` decrypts with the caller's passphrase to the plaintext
of a secret stored `allow_unattended=false`. Same result with no `Origin`
header and no session running. This is a path around vault rule 2 (a
ciphertext under the caller's own key is the plaintext) and around the
scope and attended-only backstops. Only project-scoped entries are
reachable (`scope_filter` is always the project id); a locked passphrase
vault exports nothing. Smallest fix: `_require_human_passcode(data)` in the
route whenever `vault is True`, and have the export loop refuse `oauth.*`
and write a per-entry audit line. Tests pin the open behaviour:
`tests/test_backup_unattended_gate.py`
(`test_no_agent_session_at_all_is_the_spa_case_and_still_succeeds`,
`test_unattended_session_on_a_different_project_does_not_block_this_one`).

**P27 — `mc/backup.py:1580-1614`, `:1699-1715`, `:1173-1194` — M — high.
Import and restore write wherever the archive says.**
`_remap_import_dest` joins member-name segments onto a base path without
checking the result stays under it, and member names come from the
archive's own manifest. **Measured**: `records/memory/<id>/../../../../../x`
resolves five levels above the memory directory;
`records/projects/..\..\..\x.json` (one segment to `split('/')`, three
levels to Windows) leaves `data/projects`; `unprotected/nongit/<id>/../../x`
leaves the project path. Import is the cross-machine path by design, so the
archive is someone else's file: one hostile project archive is an arbitrary
file write as the server user (a startup script, a hooks file). Import also
never calls `_validate_records_write`, so `records/projects/<any>.json`
lands in `data/projects` and becomes a "project" (the DATA_DIR rule), and
an imported `.mcp.json` is written into the project (`:1598`) while imported
schedules are deliberately disabled (`:1727`); whether the runtime asks
before starting a project's MCP servers was not checked. Full restore
(`restore_backup`) writes each member to the absolute `dest` recorded in
the manifest with no containment check at all; it is "same machine" by
intent, and nothing verifies that. Both sit behind the passcode, so this
needs a human to import or restore a file they did not make. Smallest fix:
reject any member name holding `..`, a backslash, a drive or a leading
slash; resolve every destination and require it to be inside the root that
branch computed; run `_validate_records_write` on import; for restore,
accept a `dest` only under one of the `_paths()` roots or a registered
project path. Tests round-trip archives this module wrote.

**P28 — `mc/blueprints/backup_routes.py:665-669`, `:643-647`, `mc/backup.py:1823-1824`, `:2005-2011`, `:1987-2002` — M — high.
Restore-point routes turn URL segments into filesystem paths, and DELETE is ungated.**
`project_id` and `snap_id` go straight into `restore_points_dir / project_id
/ snap_id`. `delete_restore_point` then `shutil.rmtree`s that directory if
it holds a `manifest.json`. **Measured** (test client, Windows):
`DELETE /api/backup/restore-point/foo/..%5C..%5C..%5Cunrelated_app` → 200
and a directory outside the restore-point tree, holding a `manifest.json`,
is gone. No passcode, no unattended check ("no gate", `:99-101`), so any
caller that can reach the port can recursively delete any directory that
has a `manifest.json` at its top (a web app, a browser extension source
tree). PATCH rewrites that directory's `manifest.json` with a label or pin;
GET lists it. On POSIX a segment cannot hold a separator, so only
`project_id='..'` works there. Read, not measured against the live server.
The same missing check lets a `label` with separators place a new archive
outside the chosen directory on Windows (`mc/backup.py:842`, `:1434`).
Smallest fix: accept `project_id` only if it is a registered project and
`snap_id` only if it matches the stamp-and-slug shape this module writes;
resolve and require containment; slug the archive label as
`_slugify` already does for restore points. No test sends a hostile id.

**P29 — `mc/backup.py:1154-1161`, `:1690-1697`, `:745-746`, `:883-886` — E/F — high.
Restore and import load the whole archive into memory; create loads each file whole and drops what does not fit.**
Both stage every selected member as bytes in a list before the first write.
**Measured**: peak traced memory 67 MB restoring a 64 MB archive. The
module's own comment (`:848`) gives 44.8 GB for the default archive on the
development install, so a full restore of that archive needs about that
much memory and cannot complete on an ordinary machine. On create,
`read_bytes()` plus `writestr` holds each file twice; a file too large for
memory raises `MemoryError`, which the `except Exception` at `:883` records
as a `parse failed` warning and skips, so the largest files are the ones
silently missing from a "complete" backup. Smallest fix: verify hashes in a
first streaming pass (`zf.open` + chunked `hashlib`), extract in a second
(`shutil.copyfileobj`); on create, stream with `zf.open(arcname, 'w')`
while hashing. Tests use kilobyte fixtures.

**P30 — `mc/backup.py:1272`, `:1319`, `:1841`, `:1591`, `:1130` — L — medium.
"This project's files" is a name-prefix test, so project `a` owns project `a_b`'s files.**
Export, restore points and rollback select `data/projects` entries with
`name.startswith(f'{pid}_')` and uploads the same way. **Measured** with
projects `foo` and `foo_bar`: the export of `foo` carries `foo_bar.json`,
`foo_bar_agent_log.json` and `foo_bar`'s upload; a rollback of `foo`

That is one project's rollback silently reverting another project's log.
Project ids with underscores are the norm; the running install has 23
projects and no such pair today, so this is latent here. Smallest fix: a
single `_owns(pid, name, all_ids)` that accepts `pid + '.json'` or `pid +
<known sidecar suffix>` and rejects a name a longer registered id also
matches; use it in all four places.

**P31 — `mc/backup.py:2140-2141`, `:1921`, `:1975-1981` — L — medium.
Rolling back to the oldest restore point deletes that restore point.**
`rollback` takes a `pre-rollback` snapshot first; creating it runs

**P32 — `mc/backup.py:1194`, `:1715`, `:2160`, `:1256`, `mc/blueprints/settings_routes.py:495` — L — medium.

**P35 — `mc/backup.py:735-742`, `:843`, `:926`, `:256-259` — L/M — low.
