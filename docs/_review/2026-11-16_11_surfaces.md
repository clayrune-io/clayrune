#### SF1 · high · lens 2/3 — an unreadable `~/.claude.json` or `.mcp.json` is treated as empty and then overwritten

`mc/mcp.py:167-180` (`_read_json_or_empty`) returns `{}` for a missing file,
an empty file, a read error (`except Exception`, `:172`) and a parse error
(`:178`) alike. `_write_global_servers` (`:197-204`) and
`_write_project_servers` (`:219-226`) read through it and then atomically
replace the file with `{"mcpServers": {...}}`.

Failure: the file exists but cannot be parsed at the instant of the read (a
UTF-8 BOM, which Windows PowerShell 5.1 and Notepad write; a file another
process left truncated; a sharing violation on Windows, which lands in the
`except Exception` at `:172`). The next panel Save, Delete, URL install or
boot-time built-in install writes a file holding only the one new server.
Every other server is gone, and for `~/.claude.json` so is every other key
Claude Code keeps there (account, per-project state, its own settings).

Measured (scratch copy, module path patched to a temp file): a healthy file
keeps its three keys; the same file cut in half becomes
`{"mcpServers": {"new": ...}}`; a project `.mcp.json` with a BOM, one server
and one other key becomes a file with only the newly written server.

The same read also makes `list_servers` (`:269`) show an empty fleet for a
BOM file, which is what invites the Save that destroys it. The dispatch trim
reads through the same function (`mc/session_mcp_launch.py:28-33`), so a BOM
project file silently drops that project's servers from non-Claude launches.

Fix: split the read. Missing or empty stays `{}`; a read or parse failure
raises in the two write paths (refuse the write, name the file) and logs in
the read paths; decode with `utf-8-sig`. Test: none. No test file exercises
`mc/mcp.py` CRUD against a damaged file (`tests/test_mcp_write_gate.py` and
`tests/test_mcp_trim.py` use healthy fixtures).

#### SF2 · high · lens 3 (security) — `POST /api/mcp/url/preview` has no gate and feeds cloned source to a tooled `claude -p`

`mc/blueprints/mcp_routes.py:300-401`. Every other write route in this file
starts with `refuse_unattended` and most add `require_passcode`
(`:123`, `:162`, `:196`, `:251`, `:422`). The preview route has neither, and
it is the route that does the work on untrusted input:

- clones any URL the caller names (`:376`) through the unhardened branch of
  `stage_clone` (`mc/mcp_installer.py:276-279`: hooks path, global and system
  git config are neutralised only when `staging_id` is passed, and the panel
  passes none);
- runs `npm install --package-lock-only --ignore-scripts` in the clone when
  it has no lockfile (`mc/mcp_installer.py:591-596`, reached from `:385` with
  `read_only` left False);
- calls `security_scan(install_dir, sha)` (`:386`) with `toolless` left False,
  which is `claude -p <prompt + up to 20,000 bytes of the repo's source>
  --max-turns 1 --output-format json` (`mc/mcp_installer.py:800-804`): a full
  Claude Code process with the user's tools, settings allowlist and global
  MCP fleet, reading text a stranger wrote.

`docs/UNTRUSTED_INPUT_SURFACE.md:46` records the second half as "not yet
migrated"; the 2026-09-10 security review listed path 1 as open. What is new
here: (a) the hardened twin already exists and is used by Desk Connect only
(`mc/desk_connect/github_connection.py:37,45`: `staging_id=` and
`toolless=True`), so the two "install from GitHub" flows now differ in
exactly the protections that matter; (b) the route is callable by an
unattended agent, so a session that has read hostile text can point a tooled
Claude process at a repository of the attacker's choosing without a human.
That is one step short of the brief's blocker line (nothing is registered
without the passcode at `:455`), hence high.

Fix: `refuse_unattended('preview an MCP server install')` first; pass a
`staging_id` and `toolless=True`, `read_only=True` exactly as
`github_connection.py` does; delete the tooled branch
(`mc/mcp_installer.py:800-816`). Test: `tests/test_mcp_write_gate.py` covers
the five gated routes; nothing asserts the preview route refuses anyone.

Also on the tooled branch, read, not measured: the prompt is passed as one
argv element. Where `claude` resolves to the npm `.cmd` shim (`:433-436`) the
launch goes through `cmd.exe` and its 8,191-character line, so a repository
with more than about 8 KB of source would fail the scan with `claude rc=1`
and the panel would show "scan unavailable" for exactly the larger servers.

#### SF4 · medium · lens 2 — the Python dependency audit audits Clayrune's own environment, not the server being installed

`mc/mcp_installer.py:688`: `pip-audit -f json` with `cwd=<clone>`. pip-audit
takes the project as a positional `project_path` or a requirements file as
`-r`; with neither it audits the Python environment it runs in (measured:
`pip-audit --help` on 2.10.0, "project_path ... default: None", "audit the
Python environment"). `shutil.which('pip-audit')` (`:686`) finds the copy in
Clayrune's own virtualenv, so the advisories shown under a Python MCP
server's preview are Clayrune's dependencies, and a server with a vulnerable
pin shows clean. Not run end to end (it calls an external advisory service).

Fix: `['pip-audit', '-f', 'json', '.']` for `pyproject.toml`,
`['pip-audit', '-f', 'json', '-r', 'requirements.txt']` otherwise. Test: none.

#### SF5 · medium · lens 2 — Python MCP servers are pip-installed into Clayrune's own interpreter

`mc/mcp_installer.py:843-848`. Without `uv` on PATH the install command is
`sys.executable -m pip install -e .` (or `-r requirements.txt`), run in the
clone (`:862`). `sys.executable` is the interpreter running the server, so a
stranger's dependency pins are resolved into Clayrune's virtualenv; a server
that pins an older Flask or `cryptography` downgrades the app's own
dependency and the damage shows at the next restart. In a frozen build
`sys.executable` is the application binary, and `Clayrune -m pip ...` starts
a second copy of the app rather than pip (read, not run; the other modules
that shell out to Python guard on `sys.frozen`, e.g.
`mc/session_mcp_config.py:50`, this one does not).

Fix: create a virtualenv inside the install directory and install there
(and point the written `command` at it), or refuse Python installs without
`uv`. Test: none.

`mc/mcp_launch_config.py:14,86,101,108-116`. Every Codex, Goose and Kiro

#### SF8 · high · lens 2/4 — on Windows the stdio server runs in the locale code page: a reply with a character outside it kills the server, and non-ASCII arguments arrive corrupted

`mc/clayrune_mcp/protocol.py:99-103,106` reads `sys.stdin` and writes
`sys.stdout` as text with `ensure_ascii=False`. `server.py:25-36` never
sets an encoding. The process is started as `sys.executable server.py ...`
(`mc/session_mcp_config.py:54-55`) with no `-X utf8` and no environment of
its own. MCP frames are UTF-8.

Measured (Python 3.14 on Windows, `PYTHONUTF8` and `PYTHONIOENCODING`
unset, which is what an agent's tool process on this install inherits: both
read `None` from a Bash tool call in this session):

- stdin and stdout are `cp1252`. A tool that returns text containing `→`
  ends the process: exit code 1, `UnicodeEncodeError` on stderr, no reply to
  that call and none to the `ping` after it. The session has lost all eight
  tools. `clayrune_list_agents` returns other sessions' task text and
  `clayrune_coord_events` returns free-text summaries, so this is the normal
  case on a project whose tasks contain an arrow, a check mark or an emoji.
- an argument `dash — arrow →` reaches the handler as `dash â€” arrow â†'`
  (mojibake), and `"hello"` in curly quotes reaches it with a lone surrogate
  (`\udc9d`), because byte 0x9D has no cp1252 mapping. `_send_message` and
  `_dispatch_agent` forward that text to the target session as the message
  or the task (`tools.py:278`, `:295`).

`app.py:516` sets `PYTHONIOENCODING=utf-8` only under `__main__` of the
desktop entry point; a server started any other way does not have it, and a
CLI is free to launch a stdio server with a reduced environment anyway.

Fix, in `server.py:main` before `protocol.serve`:
`sys.stdin.reconfigure(encoding='utf-8')` and
`sys.stdout.reconfigure(encoding='utf-8', newline='\n')`. Test:
`tests/test_clayrune_mcp_protocol.py` drives `serve` with in-memory text
streams, which have no encoding, so it cannot see this.

#### SF9 · medium · lens 2 — the fence check for `clayrune_dispatch_agent` and `clayrune_send_message` asks about a different request than the one sent

`mc/blueprints/clayrune_mcp_routes.py:32-35`: the fence is asked about

#### SF11 · medium · lens 2 — an adoption card whose binary changed can never be approved; Retry fails for good

same stale snapshot.

Measured: after the failure, re-filing with a changed binary returns
`existing` and the stored hash is unchanged.

Fix: on `existing` with kind `adopt`, replace `adoption` with the fresh
inspection (and reset `failed` to `pending` so the human sees the new path
and hash before approving). Test: none.

  finding at today's call rate (per render); it would be one on a poll path
  (`mc/desk_engines.py:2077` calls it to build a plan view).

#### Sound

- Extraction never uses archive paths; members are looked up by exact
  catalogued name and must be regular files (`installer.py:118-158`).
- A checksum mismatch is a hard stop, staging is always removed, the
  manifest is written only after the atomic rename.
- `claim` is first-wins under a lock; an `installing` record with no worker
  is failed at boot (`request_store.py:156-166`, `:200-212`).
- The agent's reason is stripped to one plain line and shown as quoted text
  (`request_store.py:47-52`, `service.py:92`).
- Decline is keyed on the base id, so rewording or switching to `system:`
  raises no new card.
