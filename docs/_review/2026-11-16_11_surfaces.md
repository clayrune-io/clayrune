### 5.9 Terminal pop-out (`mc/blueprints/terminal_routes.py`)

Read in full (515 lines).

#### SF20 · high · lens 2/4 — the terminal stream goes permanently silent after 5,000 output chunks

`terminal_routes.py:107-110` (and `:140-142` for PTY) trims the buffer:
past 5,000 chunks it keeps the last 3,000. `terminal_stream` follows the
buffer with a list index (`:377-384`): emit `lines[sent:]`, then
`sent = len(lines)`. After the first trim `sent` is 5,000 and the list
never again holds more than 5,000 entries, so `sent < len(lines)` is never
true again.

Measured (`_scratch/sf_term_trim.py`, the two loops copied, one poll per
chunk, which is the stream's best case): 20,000 chunks produced, 5,000
delivered, first undelivered chunk number 5,001. Nothing after it arrives.

A chunk is one `os.read`, so a dashboard that repaints a few times a second
gets there in well under an hour. The pop-out is documented for exactly
that: "a visual command, dashboard, server, or any long-running process".
The process keeps running and `status` stays `running`, so nothing tells
the user the view is dead. A page refresh re-reads the buffer through
`/terminal/status` and works until the next trim.

Smallest fix: keep a running `dropped` count on the session, incremented by
the number of entries the trim removes, and index the stream by absolute
position (`lines[sent - dropped:]`). `tests/test_terminal_routes.py` does
not produce 5,000 chunks.

#### SF21 · medium · lens 2 — Stop kills the shell, not the command

`:240-250` starts the command with `shell=True`. `_kill_terminal_session`
(`:285-293`) calls `proc.kill()`, which ends that one process: `cmd.exe` on
Windows, `sh` on POSIX. The command it started is a child of the shell and
is not touched. `terminal_stop` then sets `status = 'stopped'` and prints
"Process stopped by user" (`:469-471`), and `_unregister_process` removes
it from the process ledger (`:293`), so the Process Manager stops showing a
process that is still running and still holding its port.

The runtime already has the tree kill this needs
(`agent_runtime.py:3684`, `taskkill /F /T /PID`).

Evidence: read, not measured (measuring needs a spawned process tree).

Smallest fix: on Windows `taskkill /F /T /PID`; on POSIX start the shell in
its own session and `os.killpg`.

#### SF22 · high · lens 3 (security) — connecting a GitHub repo and enabling code sync are ungated, and both publish

`project_routes.py:2100-2125` (`POST /api/project/<id>/github/setup`) and
`:2170-2179` (`POST .../code-sync/enable`) check only that the project
exists. No passcode, no `is_agent_caller`, no unattended refusal. Neither
`github_repo` nor `github_sync_enabled` nor `code_sync_enabled` is in
`PROJECT_SAFETY_KEYS` (`mc/project_safety_settings.py:16-29`), and these
routes would bypass that list anyway.

What one POST does:

- `github/setup {"repo": "owner/name"}`: `validate_repo` accepts any repo the
  local `gh` login can view (`github_sync.py:110-117`), the route saves it,
  and a background thread runs `sync_project` at once (`:2121-2124`).
  `_push_items` then creates a GitHub issue for every backlog item that has
  no issue number, title from the item text and **body from the item's notes
  joined** (`github_sync.py:394-406`), 25 per cycle (`:54`, `:386`), and the
  scheduler repeats that every five minutes (`scheduler_routes.py:922-935`)
  until the backlog is exhausted.
- `code-sync/enable`: `git worktree add -b <prefix>/<install id>` off the
  project's current `HEAD`, an append to the project's `.gitignore`, then
  `git push -u <remote> <branch>` (`project_sync.py:219-233`, `:428`). The
  branch carries every local commit the remote does not have yet, and its
  name embeds the machine's hostname (`:93-95`; `mc/update_ping.py:8-9` calls
  that out as the reason the ping uses a different id).

**Failure:** an agent session (or text that steers one) sends one loopback
POST naming a public repo the operator's `gh` login can see. Within seconds
25 backlog items, with their notes, are public issues; 25 more follow every
five minutes. Watchers of the repo are notified by GitHub. Nothing in the
product asks a human, and neither step can be taken back by Clayrune.
Backlog notes are exactly the operator-specific text the repo's own rules
keep out of git.

**Smallest fix:** put both routes behind the gate the other human-only
project writes use (`require_human_routing_write` /
`_require_human_passcode`), and refuse an attributed agent caller first.
`github/disconnect` and `code-sync/disable` can stay open.

**Tests:** `tests/test_github_sync_harness.py` and `test_github_sync_p0.py`
exercise the module with a fake `gh`; no test posts to `/github/setup` or
`/code-sync/enable` as an agent (grep for `github/setup`, `disconnect`: 0
hits in both files).

#### SF23 · medium · lens 2 — both syncs save a project record they loaded before the network calls

`github_sync.py:478` loads the record, `:488-489` run `gh issue list` and up
to 25 `gh issue create` plus 25 `gh issue edit` (each with a 30 s timeout,
`:122`), `:428` and `:492` save the copy loaded at `:478`.
`project_sync.py:458` loads, `:475` runs `git fetch` (120 s timeout,
`:273`), `:478`/`:491` save.

`save_project` rescues only **additions** made by another writer in that
window (`project_routes.py:302-342`, `_reconcile_concurrent_additions`: an
item is restored when its id is on disk and not in the stale copy). An
**edit** to an existing item, or a **deletion**, is not: the stale copy has
that id, so the stale version wins.

**Failure:** GitHub sync is on. The five-minute tick starts a sync; while
`gh issue list` is in flight a user marks a backlog item done (or an agent
PATCHes its text). The sync's save at `:492` writes the item back as it was
at `:478`. No log line, because the reconcile sees nothing to rescue. The
window is one network round trip on a quiet cycle and minutes on a cycle
that creates issues.

Both syncs also run inline on the scheduler loop thread
(`scheduler_routes.py:935`, `:957`), so a slow `gh` or `git fetch` delays

120 s per project for code sync.

**Smallest fix:** do the network work first into a list of intended changes,

scheduler loop.

**Tests:** none drives a concurrent edit; the fakes return instantly.

#### SF24 · medium · lens 2 — pushing an item rewrites its local text, and an item GitHub rejects is retried forever

`github_sync.py:380` builds the issue title as `sanitize(item text)`;
`sanitize` strips anything shaped like `<...>`, cuts at 1,000 characters and
trims (`:80-89`). After a successful create, `:417` stores that string back
as the item's own text ("so future compares converge").

Measured on the pure function: a 5,000-character text comes back 1,000 long;
`a <b> c` comes back `a  c`. Measured on this install's backlog over GET: 57
of the 95 live items are longer than 1,000 characters, and 50 items contain
a `<...>` span.

Two outcomes, both wrong:

- GitHub accepts the title: the backlog item now holds the stripped and cut
  text. The original is gone (the project record is not in git).
- GitHub refuses it (issue titles have a length limit well under 1,000; not
  measured here): `new_num` stays `None`, nothing is recorded, and the same
  item is tried again on every cycle. Each try counts against the 25-create
  cap (`:407`), so 25 such items ahead in the list stop every later item
  from ever being pushed, at 25 failing API calls every five minutes.

**Smallest fix:** never write the sanitized title back; compare through
`sanitize()` instead. Send the first line (capped to GitHub's limit) as the
title and the full text in the body. Record a per-item push failure and skip
it until its text changes.

**Tests:** `test_github_sync_harness.py:36` checks `sanitize` strips a
