### 1. Reported test launcher: `tools/test-run.py`, `test_run_launcher.py`, `test_run_transport.py`, `test_run_pytest.py`, `test_run_node.py`

Sound: exact argv is preserved, a refused or switched-off capture always falls
back to running the original command, the manifest parser rejects duplicate
keys, non-finite numbers and oversized input, telemetry is bounded and its
failures never change the command's exit code, and nothing but sanitized codes
crosses the transport boundary.

**TL1 (L, high). A timeout or cancel ends only the direct child; the tests keep running.**
`tools/test_run_launcher.py:226-233`. `proc.kill()` targets the one PID the
launcher started. Every `--shell` unit, and any argv unit whose program spawns
workers (a shell wrapper, `npm`, pytest-xdist, a smoke that launches a
browser), leaves its descendants alive. The launcher then reports
`termination: timeout`, finalizes the run and exits while the test process is
still writing files and holding ports.
Measured: `--timeout-seconds 1 --shell bash --command "python child.py marker; echo done"`
with a child that sleeps 6 s and then writes a marker. The launcher exited
with code 1 after 3 s and warned `output_drain_incomplete`; the marker file
appeared 5 s later.
Second effect, same lines: the surviving grandchild holds the pipe, so both
pump threads never see EOF and the tail of the output is lost
(`:241-246` joins for one second, then gives up).
Smallest fix: start the child in its own process group (POSIX
`start_new_session=True` and `os.killpg`; Windows a Job Object with
kill-on-close, or `CREATE_NEW_PROCESS_GROUP` plus `taskkill /T /PID <own pid>`).
That still only ends processes this launcher started. Test:
`tests/test_test_run_launcher.py` has timeout cases against a direct child
only; none starts a grandchild, so none catches this.

**TL2 (L, low). The "never WSL" guard misses the second WSL launcher.**
`tools/test_run_launcher.py:54-57`. Only `System32\bash.exe` is rejected.
Windows also ships a WSL alias under the per-user `WindowsApps` folder; on
the review box `where bash` lists three: Git's, System32's and that alias. If
the alias is first on PATH, `--shell bash` runs the command inside WSL, the
substitution the comment at `:52` says never happens. Read, plus the `where`
listing. Fix: reject any resolved path whose parent is `WindowsApps` too.
No test covers it.

**TL3 (E/L, low). One queue slot per event, and `finalize` is droppable.**
`tools/test_run_pytest.py:93` and `tools/test_run_node.py:105` enqueue every
sidecar record separately into a 256-slot queue
(`tools/test_run_transport.py:19`, `:79-87`). The worker batches to 64 only
after dequeuing. If one loopback POST stalls (2 s budget, `:17`) a suite
emitting more than about 130 events a second overflows the queue, and
`send('finalize', ...)` (`test_run_launcher.py:280`, `:292`) goes through the
same `put_nowait`: a dropped finalize leaves the run open on the server with
only a stderr line (`:189`). Read, not measured. Fix: enqueue one item per
read batch, and make `finalize` a blocking put with a short timeout.

**TL4 (E, low). Process registration blocks output for up to 2 s per unit.**
`tools/test_run_launcher.py:212-216`. `client.register` is a synchronous
HTTP call made before the pump threads start. With the server down each unit
pays the full connect timeout before a byte of its output is relayed
(measured above: 1 s timeout unit took 3 s). Fix: register from the telemetry
thread, or start the pumps first.

### 2. `tools/with-secret.py`

Sound: a missing secret never starts the child; the unattended flag can only
add strictness; the locked-vault fallbacks keep the value in the server;
`_resolve_program` and `NoDefaultCurrentDirectoryInExePath` close the
planted-binary path and have tests (`tests/test_with_secret_node_plant.py`).

**TL5 (M, medium). A multi-line secret is echoed unredacted.**
`tools/with-secret.py:345-347` scrubs the child's output one line at a time
with `vault.redact`, which is a whole-value substring replace
(`mc/secrets_store.py:2124-2136`). A value that contains a newline (a PEM
key, a service-account JSON, any pasted multi-line token; `set_secret` at
`mc/secrets_store.py:2240` does not refuse one) never fits inside a single
line, so no line matches and the whole value reaches the transcript.
Measured: `register_dispensed` with a four-line value; `redact` on the whole
string replaced it, the same text fed line by line came back unchanged.
The server-side fallback does not have this hole: it uses an incremental
`StreamRedactor` (`mc/secrets_exec_stream.py:20`). Two paths that claim the
same guarantee and differ. Fix: use the same stream redactor here, or redact
each line of a multi-line value as its own needle. No test covers a
multi-line value (`tests/test_with_secret_*.py` are about unset, node plant
and exec fallback).

**TL6 (L, low). stderr is merged into stdout.**
`tools/with-secret.py:322` (`stderr=subprocess.STDOUT`). A caller that
parses the child's stdout (`... -- gh api ... | jq`) receives the child's
warnings in the same stream and fails to parse. `--raw` keeps them apart but
drops redaction. Fix: a second reader thread for stderr with the same scrub.

**TL7 (M, low). A child that cannot start is a traceback and exit 1.**
`tools/with-secret.py:309`, `:319`. `FileNotFoundError` and
`PermissionError` from `Popen` are not caught. On Windows this is the normal
result for a `.cmd` shim named without its extension (`npx`, `npm`):
`_resolve_program` tries `name + '.exe'` only (`:189`). The docstring
(`:56-58`) says the exit code is the child's or 2; a caller cannot tell this
1 from a child that ran and failed. Fix: catch `OSError`, print one line,
return 2 (or 127).

### 3. `tools/cli-version-check.py`

Sound: enumeration failure is kept distinct from "no lockers" everywhere;
`--apply` has no local-install fallback; `_run` never raises and closes stdin.

**TL8 (L, low). An unknown latest version reads as `ok`.**
`tools/cli-version-check.py:412-421`, `:464-470`. `_cmp` returns 0 when either
side is missing, so `behind` is false and the row keeps `status: 'ok'`. On a
machine with no npm (the case the docstring at `:205` records) or no network,
every npm-tracked CLI is reported `ok` and the exit code is 0. The file's own
header says a version auditor that hides what it could not check is the
failure it exists to prevent. Fix: `status: 'unknown'` when `npm_package` is
set and `latest` is `None` (same for an unparseable installed version).
`tests/test_cli_version_check.py` does not cover it.

**TL9 (L, low). A symlinked PATH directory is reported as a shadow copy.**
`tools/cli-version-check.py:175-188` compares `os.path.abspath` of
directories, which does not resolve links. On a merged-`/usr` Linux both
`/usr/bin` and `/bin` are on the default PATH and are the same directory; a
CLI installed there is listed as shadowed by itself, the row is `shadowed`
and the run exits 1 every day (`:694-695`). The `--apply` path adds the same
check to the server's rows (`:665-667`). Read, not measured. Fix:
`os.path.realpath` for both sides, and compare the resolved file as well.

**TL10 (E, low). `npm config get prefix` and the process listing are repeated per CLI.**
`tools/cli-version-check.py:446-449`: for each npm-managed CLI,
`npm_package_dir` and `aside_dir_for` each spawn `npm config get prefix`
(`:192-197`, `:244`, `:264`), `_prefix_fallback` spawns it a third time when
the CLI is not on PATH (`:125`), and `list_processes()` runs a full
PowerShell process query once per CLI. Four npm CLIs: 8 to 12 npm spawns and
4 process queries for values that do not change within a run. Read, not
measured. Fix: compute both once in `main()` and pass them down.

Streamlining ST1 covers the local update path in this file, which `main()`
no longer reaches.

### 4. `tools/clayrune-backup.py`

Sound: no import of the server, so it works when the server will not start;
import defaults to a dry run; restore verifies every hash before any write
(`mc/backup.py:1152-1161`).

**TL11 (M, medium). The vault passphrase is taken on the command line.**
`tools/clayrune-backup.py:278`, `:292` (`--passphrase <p>`, shown in the
usage text at `:19`). A passphrase typed there lands in shell history, in the
process list, and, when an agent runs the command, in the transcript and
whatever is distilled from it. `CLAUDE.md` ("credentials go in the vault,
never in a command line") names exactly this. Fix: read it from an
environment variable or a prompt (`getpass`), keep the flag only as
`--passphrase-env NAME`.

**TL12 (L, medium). `restore` exits 0 when files were refused or failed to write.**
`tools/clayrune-backup.py:237-243`. `restore_backup` collects per-file
`OSError`s and refusals in the report and does not raise
(`mc/backup.py:1178-1197`); the CLI prints the first ten and returns 0. A
restore onto a full or read-only disk writes nothing and reports success to
any script or agent that checks the exit code. This is the documented
recovery path for a server that will not start. Same function: a bad zip, a
missing `manifest.json` (`:223`) and any `BackupError` other than the
integrity one are uncaught tracebacks, and `create` (`:95-108`) catches
nothing at all. Fix: return 1 when any category has `errors` or `refused`,
and wrap both commands in the `except bk.BackupError` that `import` already
has. `tests/test_backup*.py` exercise `mc/backup.py`, not this exit code.

### 5. Windows launch helpers: `tools/clayrune-autostart.ps1`, `tools/_mc_restart.ps1`

Sound: `clayrune-autostart.ps1` derives its directory and port instead of
hard-coding them, probes before launching, and confirms the port answers
before reporting success. The probe-then-start race between the boot task and
the logon window task (`:140-146`) is real but harmless: the server's own
exclusive bind (`mc/listen_socket.py:5-19`) makes the loser exit.

**TL13 (L/M, medium). `_mc_restart.ps1` kills by command-line pattern and cannot restart the default launch.**
`tools/_mc_restart.ps1:32-41`. It tree-kills every `python.exe` on the machine
whose command line contains `server.py`. Two wrong results from the same
filter:
* It is too wide. Any other project's `python server.py`, and this repo's own
  mail MCP server (`tools/mail-mcp/server.py`, started as
  `python .../server.py` under an agent CLI), match and are killed with their
  trees. The project's process rule is "only PIDs you started".
* It is too narrow. `clayrune-autostart.ps1:73` prefers `pythonw.exe`, which
  the `Name='python.exe'` filter never matches. For a server started by the
  supported autostart the script logs "no running server.py process found",
  waits 30 s for a port that is never released, then starts a second server
  (`:55`) that loses the exclusive bind. If the old server still answers,
  `:64-69` logs "heartbeat OK: True" for a restart that did not happen.

Also `:48`, `:64` hard-code port 5199 while the sibling script reads
`MC_PORT`/`config.json`, and `:16-18` relaunches with whatever `python.exe`
is on PATH while the sibling prefers `.venv` because "the system python may
not have Flask at all". Read, not run. No caller in the repo (grep:
`.gitignore:390` and `docs/SECRETS.md:432` only); see streamlining ST3.
Fix if kept: take the PID from the listener on the resolved port
(`Get-NetTCPConnection -LocalPort $port -State Listen`), kill that PID's tree
only, and share `Resolve-Port`/`Resolve-Python` with the autostart script.
No test.

### 6. Backlog journal tools: `tools/backlog_journal_common.py`, `backlog-journal-export.py`, `backlog-journal-migrate.py`, `backlog-key-backfill.py`

Sound: export and migrate share one classifier and one filename function, so
they cannot disagree about which notes move; migrate refuses an item whose
journal is missing and keeps its backup outside the project-records
directory; key backfill reuses the server's own numbering function, loads
every record before deriving keys, and mirrors the sidecar exclusion.

**TL14 (L, high). Re-running the export overwrites every journal that belongs to an item with notes.**
`tools/backlog-journal-export.py:46-85`. `write_journal` builds the file from
the item's current notes and calls `path.write_text` unconditionally (`:84`).
The journals are the append-only log agents are told to write to, the
directory is gitignored, and the agent rules name this script as the way to
regenerate `INDEX.md`. `backlog-journal-migrate.py:68-75` leaves one pointer
note on every item it migrates, so every migrated item still "has notes" and
is rewritten on the next export, to a file holding only the notes that
remain. Anything an agent appended, and the moved notes whose only surviving
copy is that file (`backlog-journal-migrate.py:4-6`), is gone, with exit
code 0 and a count of files "written".
Measured on synthetic data: write a journal for an item with one note, append
an entry, call `write_journal` again; the appended entry is not in the file.
Measured on this install, read-only, writing only to scratch: 171 items carry
notes, 161 of them have an export-named journal, and all 161 are
byte-identical to a fresh export. So nothing would be lost today, and that
same number says the export has been re-run since the last note change and
no appended entry survives in any of those files; whether one ever existed
cannot be told from here.
Smallest fix: never rewrite an existing journal. Write only when the file is
absent; otherwise append the notes whose timestamp heading is not already in
it. Regenerating `INDEX.md` should be possible without touching journals
(`--index-only`). No test exists for this tool at all.

**TL15 (L, low). A journal's filename is derived from the item's text, so it changes when the text does.**
`tools/backlog_journal_common.py:46-49`. The agent rules tell agents to PATCH
an item's text when its state changes. The next export then writes a second
file under the new slug and lists the old one as an agent-written orphan
(`backlog-journal-export.py:121-135`); migrate skips the item because the
expected file "is missing" (`backlog-journal-migrate.py:64-66`). Agents that
start a journal by hand pick their own slug as well. Measured on this
install: 324 of 485 journal files do not match the name the export would
give any item, and 44 item ids have more than one journal file. "Read your
item's journal" has no single answer for those. Fix: the id alone is the
identity; look up an existing `<id>-*.md` before deriving a name.

**TL16 (L/M, low). Migrate writes the live project record directly, non-atomically, for a reason that no longer holds.**
`tools/backlog-journal-migrate.py:45`, `:94`. It reads the whole record, edits
it and writes it back with `write_text` while the server is running. Any
server write to that project between the read and the write is silently
undone, and a request that reads mid-write sees a truncated file. The
docstring's reason (`:16-20`: the PATCH `notes` field "landed in the same
change" and the server "still holds the old code") was true for one day;
`PATCH notes` is now the documented removal path. `:72` also stamps every
pointer note "on 2026-08-15" whatever day it runs. Fix: PATCH through the
API, or retire the script (ST4).

**TL17 (L, medium). The "canonical" night-review prompt tells an unattended agent to write backlog notes.**
`tools/night-review/PROMPT.md:29` ("state why in the item's notes"), with the
header at `:1-7` and `README.md:73-75` calling this file the source of the

**TL18 (L, low). `--verify` on the SMTP path assumes Gmail and self-send.**
`tools/night-review/send_mail.py:141-144`. The IMAP host and the
`[Gmail]/All Mail` folder are literals while the SMTP host is configurable
(`:94`, `:297`), and the check logs in as the sender. With another provider,
or with `--to` someone else, the message is delivered and the tool waits
80 s (`:104`, `:162-163`) and exits 3 "NOT DELIVERED", which callers are told
to treat as a failed send. Exit codes 4 (`:227`, paused) and 5 (`:260`,
pytest) are missing from the list at `:26-27` and from the README. The
paused refusal returns before the sender ledger is written (`:225` vs
`:242`), so refused sends leave no trace. Fix: skip verification with a
clear line unless host is Gmail and recipient equals sender; document 4 and 5;
move the ledger write above the pause check.

### 8. Mail reader: `tools/mail-mcp/`

Covered by pass 05b: the laundering path and the raw tools (MB1 to MB4). Not
repeated. Sound here: `imap_quote.py` is the one place both callers quote a
search, it escapes backslash and quote, and it sends anything with CR, LF,
NUL or non-ASCII as a literal.

**TL19 (M/L, medium). `read_email` and the `mailbox` argument are not quoted, so the "can never flag, move, or delete mail" claim is false.**
`tools/mail-mcp/server.py:186` passes the caller's `uid` to `M.uid("FETCH", ...)`
as bytes, and `:143`, `:185` and `read_digest.py:71` pass `mailbox` to
`M.select` as given. `imap_quote.py:4` records that imaplib joins arguments
into the command line unquoted; only the search query got the fix. A `uid`
that contains CRLF is therefore several IMAP commands. The read-only promise
at `server.py:11-12` rests on `SELECT ... readonly=True`, and an injected
plain `SELECT` reopens the mailbox read-write.
Measured (imaplib from the project interpreter, 3.14.0, its `send` replaced
by a capture, no network): `tool_read_email`'s exact call with a `uid` of
`1 (FLAGS)<CRLF>X1 SELECT INBOX<CRLF>X2 UID STORE 1:* +FLAGS (\Deleted)<CRLF>X3 EXPUNGE<CRLF>X4 UID FETCH 1`
put five commands on the wire, the STORE and EXPUNGE among them. That
interpreter's imaplib has no control-character guard.
Who supplies `uid`: the model, in a session that has just read sender-chosen
subject lines from `list_recent` or `search_email` (MB4). So this is the
second half of MB4: the raw tools do not only leak mail into the session,
they let text in a mail ask for the mailbox to be emptied.
Functional half of the same lines: a mailbox name with a space
(`[Gmail]/All Mail`, the name `send_mail.py:144` has to quote by hand) is sent
as two atoms and the server answers BAD, so the `mailbox` parameter the tool
schema advertises (`:217-218`, `:255-256`) works for one-word names only.
Smallest fix: `uid` must match `^[0-9]+$` or be refused; `mailbox` goes
through `imap_quote.quote` after `needs_literal` rejects it. Test:
`tests/test_mail_imap_quote.py` covers the search query only; no
test passes a hostile `uid` or a mailbox with a space.

**TL20 (L, low). A failed search is read as a list of ids.**
`tools/mail-mcp/server.py:166-167`, `read_digest.py:72-73`. Neither caller
looks at `typ` after `gmail_search`. When both the `X-GM-RAW` form and the
`TEXT` fallback are refused (any non-Gmail host, or a query the server
rejects), `data[0]` is the server's error text and its words are used as
uids; the next FETCH raises and the tool reports that second error, not the
search failure. `:144`, `:164` and `:185` ignore the result of `select` the
same way. Read, not measured. Fix: return the server's text when `typ` is
not `OK`. Also `:277-282`: a JSON line that is not an object (`[]`, `1`)
raises `AttributeError` out of `_serve` and ends the server; guard with
`isinstance(req, dict)`.

### 11. Guardrail hook generator and git hooks: `tools/guards/install_hooks.py`, `tools/git-hooks/`, `install-hooks.sh`, `install-merge-review-hook.sh`, `merge-review-check.py`

Sound: the generator writes only Clayrune-owned files and never a vendor's
global config; the merge-review installer refuses to replace a hook it did
not write and its uninstall removes only its own; the check fails closed
when it cannot find the project (`merge-review-check.py:216-219`) and checks
the exact commit, not a branch name.

**TL23 (L, medium). A damaged launch-settings file is never regenerated, and launches keep being pointed at it.**
`tools/guards/install_hooks.py:186` reads the existing destination through
`_load_json_object` (`:159-168`), which raises on invalid JSON "refusing to
read it". That read exists only to compute `changed`; the file is
regenerated from scratch (`:38-39`, `:180-182`). So a truncated file (the
write at `:248` is a plain `write_text`, not atomic) makes every later boot
raise, record `not generated` in the log and leave the file as it is.
`mc/guardrail_hooks.py:108-109` (`launch_file_if_exists`) tests only that the
file exists, so every Claude, Gemini or Qwen launch still gets the damaged
file as its settings. Either the CLI refuses to start, or it starts without
the process guard and the fence hook; the generator cannot tell which and
never repairs it.
Measured: scratch home, destination pre-filled with a truncated JSON
prefix, `generate_for_boot(installed_vendors=['claude'])` returned an error
row, the file was unchanged, and `launch_file_if_exists` returned its path.
Fix: treat an unreadable existing file as `before = {}` (it is Clayrune's own
file, there is nothing to protect) and write through a temp file plus
`os.replace`. `tests/test_install_hooks.py` has no case with a damaged
destination.

**TL24 (L, medium). The pre-push guard inspects the tip tree only, so the history it was written to stop still goes out.**
`tools/git-hooks/pre-push:25` runs `git ls-tree -r --name-only "$local_sha"`:
one commit's tree. The header (`:5-9`) gives the reason for the hook as
operator-private files that "still live in the history of old feature
branches" and would be re-published by "merging or pushing one of those
branches". A branch whose history holds such a file and whose tip no longer
