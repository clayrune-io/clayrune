## 5. Detail

### T8-1 · high · lens 2, 3: the pytest CI job never runs, and could not finish

- `.github/workflows/tests.yml:17-20`: `on: pull_request` and
  `workflow_dispatch` only. The comment at `:6-10` says this is deliberate
  because the owner pushes straight to master.
- Project practice (CLAUDE.md, "master is the release channel") is merge
  locally and push master. No pull request is opened, so the trigger never fires.
- Evidence it does not run: the workflow's run list shows one run, a pull
  request run dated 2026-06 that failed after 49 s. The frontend smoke
  workflow, which triggers on push, shows six green runs in the same listing
  for 2026-11-17 alone.
- `tests.yml:29`: `timeout-minutes: 10`. Measured on Windows: a random sample
  of 45 of 867 files (seed 1179), one process each, 1,493 tests, 169.5 s of
  in-process time, so 3.85 s per file and about 56 minutes for the suite run
  serially. Backlog MC-1149 independently records a full run at 41% after about
  25 minutes. The job would need to be more than five times faster on the Linux
  runner to finish. Not measured on Linux.
- Consequence: 13,545 tests gate nothing automatically. They run when an agent
  chooses a subset. Every HIGH in passes 01 to 12 that says "an existing test
  covers a neighbouring case" reached master through that hole.
- `.github/workflows/pyright.yml:15-18` has the same trigger and the same
  outcome.
- Smallest fix: add `push: branches: [master]` to both, and make the pytest job
  finishable: split by path into a matrix, or install `pytest-xdist` and run
  `-n auto`, with the limit raised to what a measured Linux run needs.
- Would an existing test catch it: no. It is the absence of the run.
