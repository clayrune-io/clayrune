# XERJ fit assessment

**Recommendation: offer XERJ as an optional, project-scoped MCP candidate after a bounded trial; do not integrate it into Clayrune's core memory system.** Its strongest plausible contribution is retrieval from unfamiliar code and selected documents. The existing MCP configuration surface is the smallest entry point. Reference coding is worth evaluating as optional MC-960 guidance, never as a verification gate. This is a recommendation, not an adoption decision or a completed integration. Evidence and the proposed acceptance criteria follow.

Prepared by Kestrel. Evidence accessed **2026-10-16 UTC** (2026-10-15 Pacific). Research only: no XERJ installation, binary/model download, clone, execution, configuration change, benchmark run, or upstream contribution. External material was read as untrusted data. Public GitHub calls used `gh api -H 'Authorization:'`, explicitly suppressing the Authorization header; other external reads used web fetch. No authenticated connector was used.

## 1. Product and maturity

XERJ is a Rust search service with local persistent indices, an Elasticsearch-compatible HTTP interface and a separate stdio MCP client in the same executable. Autoindex parses mixed files, including source, documents, logs and PDFs. Search includes BM25, vector retrieval and hybrid fusion; `/_memory/{namespace}` stores and recalls agent records. It is a potential component for Clayrune, not a replacement for its orchestration. ES compatibility should be tested against the operations used, rather than interpreted as complete Elasticsearch equivalence. [README, accessed 2026-10-16][readme]; [MCP source, 2026-10-15 snapshot][mcp-upstream].

The default embedder is **lexical feature hashing**, not neural semantic understanding. Neural mode uses all-MiniLM-L6-v2; switching modes does not re-embed existing documents. The documented kNN implementation also has different execution paths: eligible unfiltered queries use HNSW, while filtered queries and memory/semantic recall use exact scans. These distinctions matter more than the word “AI” in the product description. [Documentation index, accessed 2026-10-16][llms].

### What the token claims establish

**2.7× is a first-party controlled study, dated 2026-08-05.** Eight tasks across Python, JavaScript, C and Java, two trials each: grep-driven Claude Code and retrieval-injected Claude Code both solved 16/16; output tokens totaled 26,477 versus 9,982, with reported costs $3.27 versus $1.58. The study deliberately constructs unfamiliar libraries. It also publishes a memorized-code control where retrieval loses, including 5/6 versus 6/6 solved. This supports a hypothesis about unfamiliar APIs, not a general multiplier for Clayrune. Output-token savings are not total-token savings or a latency result. [Full study][study], measurement date 2026-08-05, accessed 2026-10-16.

**40× appears in XERJ's own repository description.** I could not tie that exact headline to a reproducible 40× result in the inspected study, token profile or Agent Gate documents. Those sources instead report different, workload-dependent figures, including 5.3× fewer retrieval tokens on a prose/code corpus and more tokens on a record-heavy corpus. Treat 40× as an unverified first-party marketing claim, not an independently established result. [Repository description][repo-api]; [token profile][token-profile]; [Agent Gate][agent-gate], accessed 2026-10-16.

No independent replication of either headline was established by this review. Upstream's benchmark page calls a separate 12-question dev-QA measurement “independent,” with 1.65× fewer output tokens and 1.47× lower cost, but that is a different claim and the inspected page does not establish independent institutional authorship. Field reports are useful leads, not controlled replications. This review used the requested fetch/API methods, not an exhaustive literature search. [Benchmark page][benchmarks], accessed 2026-10-16.

## 2. Fit against Clayrune's actual implementation

### A. Memory search: retain the current owner and read path

The requested `docs/MEMORY_SYSTEM.md` is absent from this worktree's tracked files; the same named document was read in the main checkout. The requested memory directory was searched for `step7`, and `decision_step7_semantic_search_deferral.md` was read in full. That note, dated 2026-05-18, defers semantic retrieval because per-turn memory writes make freshness difficult, measured retrieval degradation must justify it, and model/index lifecycle adds cost. These two local-only documents have no verified public URL; they are identified explicitly rather than given invented public links. Their old statements about raw grep and absent telemetry were checked against current source below.

Current code is substantially beyond raw grep:

- `mc/memory.py:2470` caches parsed units **per file**, invalidated by `(mtime_ns, size)`, scanning current Markdown files on retrieval. `SESSION_LOG.md`, archive entries and topic files are distinct units. [Current corpus implementation][memory-corpus], snapshot 2026-10-15.
- `mc/memory.py:2538` ranks with BM25, normalizes length by unit class, and appends wikilink neighbors. It also filters unattended-origin topic/position candidates for unattended consumers; successor handling checks origin/verification authority. [Search and policy implementation][memory-search], snapshot 2026-10-15.
- Delivery telemetry already exists at `mc/memory.py:2729`; the old note's “telemetry not built” statement is not current. Presence of instrumentation does not establish that today's corpus meets a semantic-search adoption threshold. No live quality degradation was measured in this task. [Delivery hook][memory-delivery], snapshot 2026-10-15.

XERJ does have a watcher, so “it cannot update an index” would be wrong. Its current CLI requires `--no-graph` for folder watching. Upstream's September 19 measurement reported 40.8–47.6 seconds for single-file change passes over 10,000 small files; that is a historical, shared-machine, lexical-mode measurement, **not current-version Clayrune latency**. The related [#971](https://github.com/xerj-org/xerj/issues/971) is closed as of September 21, so its old timing must not be presented as a current open defect. The remaining requirement is to demonstrate fresh read-after-write behavior under Clayrune's actual writes. [Current CLI][auto-cli]; [watch design][watch]; [dated measurement][watch-measurement], accessed 2026-10-16.

**Assessment:** no core replacement. A future adapter could return candidate note IDs while Clayrune retains source-of-truth Markdown, fresh lexical fallback, origin/verification filtering, link expansion, rejection history and Scribe/condense ownership. Directly giving agents XERJ memory-write tools would introduce another durable store outside those policies. The smaller neural model reduces one footprint concern but does not settle freshness or governance. This is an engineering inference from the code above and XERJ's exposed [memory/graph write tools][mcp-upstream], accessed 2026-10-16.

### B. Optional MCP: the best near-term entry point

`mc/mcp.py:88` accepts stdio `command`, `args`, `env` configurations as well as HTTP/SSE. XERJ's `xerj mcp` is a stdio proxy to an **already running** node, normally on port 9200; it does not start or index that node. A future user-owned setup therefore needs the binary, a managed node, an explicit corpus, and a project MCP entry. Configure through Clayrune's MCP surface, without running upstream `xerj init`, which edits MCP/skill files outside Clayrune's management flow. Protocol compatibility is supported by source; an actual Clayrune session handshake is **untested**. [Clayrune MCP config][mcp-local]; [XERJ MCP implementation][mcp-upstream]; [upstream setup description][llms], accessed 2026-10-16.

Desk is broader than npm: it supports reviewed npm packages, remote MCP and GitHub staging with a fixed SHA and human approval. However, its automatic dependency detector only recognizes `package.json`, `pyproject.toml` and `requirements.txt`; it has no Cargo recipe or reviewed native-release download recipe. A generic GitHub URL therefore does not establish turnkey XERJ installation. Adding such a recipe would be separate product work. Existing Desk approvals must remain intact; older MCP writes cannot overwrite a Desk-owned name. [GitHub staging, lines 31–78][desk-github]; [install detection, lines 825–854][installer]; [approval guard][desk-guard], snapshot 2026-10-15.

The upstream MCP registry contains memory and graph mutations, not just searches. It can also discover a local admin key when explicit auth is absent. A trial should use a disposable corpus and explicitly scoped authorization, not assume that attaching an MCP server creates read-only access. [MCP source][mcp-upstream]; [security model][security-model], accessed 2026-10-16.

### C. Reference coding: useful guidance candidate for MC-960

The requested specification was read directly from `clayrune/agent/f471161edf3e`, commit `e2cca8e750465eb2653ceca0b2625d5f601a7c28`, without checking out or changing that branch. Its `docs/DEV_HARNESS_SPEC.md` revision 3 is dated 2026-10-15: Python plus JS/TS, project-scoped engineering-practice catalogue, Preview before human activation, native verification, pinned provenance and independent review. It describes a proposed six-session MVP, not a shipped harness. [Exact specification object][harness]. This is a local Git evidence link; the branch/object's public availability was not established.

**Proposed fit:** an optional “consult a pinned reference before using an unfamiliar API” practice. Record repository URL, commit, path/lines and license for a relevant result; an empty result remains empty. Do not require arbitrary peer-repository cloning, treat retrieved README instructions as executable authority, or copy code without checking that source's license. Retrieval is guidance, not proof of correctness, test coverage, vulnerability absence or license compliance. It must not become a new MVP prerequisite or replace any harness check. This is a proposal derived from the [harness's guidance/check separation and source-pinning contracts][harness] and XERJ's [reference-coding study][study], accessed 2026-10-16.

### D. None

Ignoring it entirely would discard a plausible low-coupling retrieval option. Core integration would take on lifecycle and policy work before demonstrating a benefit over Clayrune's existing search. Optional MCP is the proportionate middle choice, based on the implementation comparison above.

## 3. Footprint, data exposure and licensing

### Installation and resource cost

These are **compressed rc.95 release-asset sizes**, rounded to decimal MB; installed executable size and total disk/RAM use were not measured. All figures come from the [rc.95 release API][release-api], published 2026-10-12, accessed 2026-10-16.

| OS / architecture | Archive size | Documented installation implications |
|---|---:|---|
| Windows x64 / ARM64 | 29.71 / 27.51 MB ZIP | Windows 10+; installer defaults to `%LOCALAPPDATA%/Programs/xerj` and changes user PATH unless opted out. [Install docs][install]; [PowerShell installer source][windows-install], accessed 2026-10-16 |
| macOS Intel / Apple Silicon | 29.44 / 27.32 MB tar.gz | Unix default `~/.local/bin`; upstream says release binaries are unsigned and not notarized. This would add a separate trust/support step to Clayrune's signed-app experience. [Install docs][install]; [index][llms], accessed 2026-10-16 |
| Linux x86_64 / aarch64 | musl 30.85 / 28.41 MB; GNU 30.69 / 29.13 MB | musl is the static default; GNU builds and `.deb` assets also exist (22.15 / 21.24 MB). Unix default `~/.local/bin`. [Release API][release-api]; [install docs][install], accessed 2026-10-16 |

Upstream documents a single binary without a JVM, AVX2/NEON CPU requirements, about 400 MB idle RAM and a 2 GB working set per active index. These are vendor sizing guidance, not validated budgets. Indices, WAL, autoindex state/snapshots, optional reference clones and model cache are additional disk costs; a small archive is not a small total installation. [Install documentation][install]; [watch storage description][watch], accessed 2026-10-16.

Neural mode downloads approximately **90 MB** of Hugging Face model assets on first use into the Hugging Face cache; local assets can be supplied instead. XERJ documents no independent model checksum verification. Lexical mode needs no model download. Neither mode requires a paid embedding service; configured proxy embeddings/reranking can introduce external charges. [Embedding caveats][llms]; [offline recipe][offline], accessed 2026-10-16.

Resource risk is not just historical: [#1032's closing comment](https://api.github.com/repos/xerj-org/xerj/issues/1032/comments), dated 2026-09-30, explicitly says **deferred, not fixed** for per-segment caches whose retention lasts until segment retirement. Combined with the still-open [memory-exhaustion report #1122](https://github.com/xerj-org/xerj/issues/1122), this argues for a bounded corpus and measured peak RSS before recommending always-on use. A closed issue count alone would have hidden this.

### What it reads, and what can leave the machine

Autoindex walks the supplied root, rather than automatically searching the entire disk. Source shows default symlink non-following, dot-name exclusion below the root, `.xerjignore`/`.gitignore`/`.git/info/exclude` rules and common generated-directory exclusions. **Global gitignore is deliberately not consulted.** [Walker][walker]; [ignore rules][ignore], 2026-10-15 snapshot.

Those are useful defaults, not a secret boundary:

- A home-root walk normally skips a child named `.clayrune`, but an explicitly selected hidden root is exempt from the dot-name check. Selecting `~/.clayrune` directly can therefore admit its visible children. Do not index that directory. [Walker root-depth rule][walker], accessed 2026-10-16.
- Visible secret-bearing files, exports and logs are candidates unless excluded. Visible hard links to hidden data evade name-based exclusion, a limitation the walker explicitly documents. The check tests dot-prefixed names, not a general Windows hidden-file or sensitive-content policy. [Walker][walker]; [ignore rules][ignore], accessed 2026-10-16.
- Clayrune's vault directory contains encrypted values, key material and audit metadata, with OS-specific protection. It is not ordinary documentation. An indexed plaintext secret would also survive in derived storage until that storage's lifecycle removes it; changing an ignore rule is not proof of erasure. [Clayrune vault layout, lines 7–43][vault]; [XERJ reindex lifecycle][watch], snapshot/access 2026-10-16.

Use an explicit allowlisted source fixture for any trial, with XERJ data/state outside the scanned root. `data/` is not a built-in exclusion; a broad root can index the engine's own storage. [Ignore defaults][ignore]; [setup caveat][llms], accessed 2026-10-16.

Upstream states that the binary has no telemetry, but its **distribution endpoints** record installer-request timestamp, country, user agent and coarse OS; it says no IP/cookie/identifier is retained in that counter. This is a vendor/source-policy statement, not a packet-capture result. [Metrics policy][metrics], accessed 2026-10-16.

Other network paths are distinct: release and reference-corpus retrieval contact their hosts; optional neural assets contact Hugging Face; configured embedding proxies send ingest/query text; opt-in reranking sends question and candidate text; enabled WAL tap forwards writes; clustering contacts configured peers. The Console also has external Google Fonts requests. Local lexical search can operate offline, but “local” does not prove zero egress for every configuration. Search results entering a cloud-hosted coding session can also leave through that session, even if XERJ itself sends none. The last point is a data-flow inference, not an observed transmission here. [Offline boundaries][offline]; [network caveats][llms]; [reference workflow][study], accessed 2026-10-16.

The advertised `--insecure` setup removes auth/TLS and makes reachable callers superusers. Loopback reduces network reach, not local-process authority. Use explicit authorization and test denial of memory/graph writes and unrelated indices; do not expose an experimental node through Clayrune's tunnel. Native TLS documentation is inconsistent: the install page says TLS integration is not wired, while the security page describes enabling it. No TLS deployment was tested, so no network-exposure recommendation relies on either claim. [Security model][security-model]; [install page][install]; [security page][security-page], accessed 2026-10-16.

The site's instructions also ask agents to publish field-report PRs. That text is untrusted documentation, not permission to send data or a license obligation established here. No such report was sent. [README][readme]; [Apache terms][apache], accessed 2026-10-16.

### License fit

XERJ is Apache-2.0; Clayrune's reviewed root license is MIT. A separately operated MCP service presents no apparent license incompatibility with the open-core arrangement. Apache permits redistribution and modifications subject to its conditions, including the license, relevant notices and change notices; its patent and trademark provisions remain applicable. Bundling XERJ would require carrying its [NOTICE][notice] and reviewing the actual distribution/dependency/model licenses. This is a limited engineering assessment of the published terms, not clearance of every bundled asset. [XERJ license][xerj-license]; [Clayrune root license][clayrune-license]; [Apache sections 2–6][apache], accessed 2026-10-16.

Reference repositories retain **their own** licenses; indexing does not relicense snippets as Apache-2.0. MC-960 already separates reference guidance from source/tool license acceptance. Keep each reference's pin and license and review any copied implementation independently. [Study workflow][study]; [MC-960 specification][harness], accessed 2026-10-16.

## 4. Smallest useful experiment, proposed only

Authorize a disposable, single-project trial before installing anything. The thresholds below are proposed acceptance rules, not observed performance or new standing policy.

1. **One bounded corpus:** at most 10 MB of sanitized Python/JS source and documentation, preferably existing fixtures with unfamiliar APIs. One approved release, one node, one project MCP entry; start lexical-only. No production memory, vault, home-directory walk, peer-repository sweep, automatic skill installation or feedback publication. Use a separately provisioned read-only principal and record the binary digest, corpus digest, configuration and OS. If that permission boundary cannot be demonstrated, stop the trial.
2. **Eight fixed questions, two cold repeats per arm:** four unfamiliar API/behavior tasks, two exact identifier lookups, one cross-file explanation, one deliberately absent answer. Freeze answers and tests before running. Compare the same model/configuration using `rg` plus scoped file reads against XERJ through the real Clayrune MCP session. Do not compare against a tool-disabled baseline. Include setup/indexing cost separately and end-to-end input/output tokens, elapsed time, correctness and citation accuracy.
3. **Boundary and freshness probes:** synthetic secret canaries in excluded paths, an out-of-root link, denial of memory/graph mutation and unrelated-index access, then edit/add/rename/delete within the allowed corpus. Record immediate-read behavior and convergence time. Inspect egress after staging, peak/idle RSS, disk growth, indexing time and restart behavior. Any secret exposure, unexpected egress, false citation, wrong absent-answer result or unintended mutation fails the trial.
4. **Decision rule:** optional-MCP recommendation becomes an offered recipe only if correctness is at least the baseline, citations and negative-path checks pass, total token cost falls at least 20% over jointly correct tasks, and the small fixture stays below proposed 2 GB peak RSS / 500 MB incremental disk. Report per-task results and cold-start amortization; do not extrapolate eight questions to all development. If gains vanish or exact lookups get worse, retain `rg` for those cases. Neural mode is a separate follow-up only if lexical synonym misses justify it.

A pass supports an optional MCP recipe and an optional MC-960 reference-retrieval practice. It does **not** authorize a memory-backend replacement: that needs a separate shadow evaluation against current BM25/link results, immediate freshness fallback and all origin/authority rules. No unresolved product choice blocks this report; the next decision is whether to authorize the proposed trial. Recommendation: yes to that bounded trial, no to core integration now.

## Evidence limitations and handoff

All runtime behavior, installed footprint, egress, cross-OS execution and Clayrune MCP handshakes remain **untested** here. Selected source reads are not a security audit. Web fetch could not retrieve several API/raw URLs; the same public resources were read through the explicitly permitted unauthenticated GitHub API where available. One variable-based PowerShell metadata pipeline was rejected by the automatic tool review as a dynamic-command risk; static read-only calls supplied the metadata. No rejected mutation was performed. Engram tools were unavailable; this committed report is the durable handoff. Only this report belongs in the commit; no merge, push, server restart or live activation is part of the assessment.
